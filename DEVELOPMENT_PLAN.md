## 1. How to use this file

**Status legend**

| Mark | Meaning |
|---|---|
| `[ ]` | Not started |
| `[~]` | In progress (at most **one** task at a time unless the user says otherwise) |
| `[x]` | Done: implemented, tested, gates green, **Evidence line filled in** |
| `[!]` | Blocked — waiting on a human decision or external account. The reason must be written on the task. |

**To make the AI work, paste this (the "kickoff prompt") into your AI tool:**

```text
You are the engineer on the Rento project. Read DEVELOPMENT_PLAN.md and README.md fully.
Follow the Task Loop in DEVELOPMENT_PLAN.md §2 exactly.
Take the first task marked [ ] whose "Depends" tasks are all [x] (or the task ID I name: ____).
Step 1 is to write the task prompt to docs/prompts/<TASK-ID>.md using the template in §3,
then execute that prompt: implement, write tests, run the gates, record Evidence,
tick the box, add a Progress log line, and stop. Do not start the next task unless I say "continue".
```

Useful one-liners for later:

| You say | The AI must |
|---|---|
| `status` | Recount the checkboxes, refresh the §8 dashboard, and list the next 3 eligible tasks. |
| `next` | Run the kickoff prompt above. |
| `do P2-22` | Run the Task Loop for that task (after verifying its dependencies are `[x]`). |
| `redo P2-22` | Re-run its gates; if they fail, reopen it (`[~]`) and fix. |
| `continue` | After finishing a task, proceed to the next eligible one. |

## 1A. MVP fast track — demo-ready backend + admin panel + mobile app (active since 2026-10-17)

**Why:** the owner wants a demonstrable MVP quickly. The full plan below stays the system of record for *production*; this section re-orders it into **vertical, demoable milestones** and relaxes the per-task ceremony. Nothing is deleted: whatever the fast track skips is listed under "After the demo" and stays `[ ]`.

### What "demo-ready MVP" means
A person can, on one laptop with one command (`pnpm demo`, built in M6) and seeded sample data:
1. **Admin panel** — sign in, manage roles and staff (invite by email), create categories/item models, drawers (with hours) and assets, see and cancel bookings, see a simple dashboard.
2. **Mobile app** — sign up / sign in with email, pick or detect a location, see nearby drawers, browse items, choose a time slot, **book (hold → pay → confirmed)**, see "My bookings", cancel.
3. **Backend** — everything above through the real API; double-booking is impossible (database-enforced), holds expire, cancellations compute the refund, every admin change is audited.

### Intentionally NOT in the demo (kept in the plan, not forgotten)
Real payment gateway (a **fake provider** behind the real `PaymentProvider` interface is used; Razorpay = P4-01…03), push/email reminders beyond account mail, Google/Meta/Apple buttons in the app (backend is done; UI = P3-13), admin MFA, rate limiting, account deletion, reports, audit viewer, extend/early-return, maintenance/transfer tools, offline mode, accessibility/performance passes, hosting/CI/backups. **Demo placeholders that need the owner's decision before real bookings:** refund tiers (README BR-9 placeholders), deposit handling (Q-3), discovery rule (top 3 within 5 km, Q-8), pickup authentication (Q-4).

### Process changes for the fast track (owner-approved 2026-10-17)
1. **One short prompt file per milestone** (`docs/prompts/M<n>.md`), not per task; tasks inside it still get their own Evidence line and tick.
2. **No stop between tasks or milestones.** At each milestone boundary, write a short report (what is demoable now) and keep going to the next milestone unless the owner says stop.
3. **Gates:** per task `pnpm check` + the targeted test files; full `pnpm verify` at the end of each milestone (and whenever a migration, contract or shared helper changed).
4. **Mutation checks** only where a bug would be expensive: booking integrity, authorization, money/refunds, token/credential handling. Other code gets ordinary tests.
5. **UI work:** component tests for logic-heavy parts + one Playwright/integration smoke per screen group; no exhaustive matrices.
6. **Engineering defaults are chosen, written in the milestone report, and revisited on request.** Stop and ask only for genuine business ambiguity (README §19.3 that blocks a screen or rule).
7. **Never relaxed:** DB-enforced booking integrity, deny-by-default authorization, forward-only migrations, RFC 9457 errors + `contracts:check`, no secrets in code/logs/app, parameterised SQL, audit of admin mutations (lean version in M1), tests must pass before ticking.

## 2. The Task Loop (mandatory protocol for the AI)

For **every** task, in this order. Skipping a step is a defect.

### Step 0 — Pick & verify
1. Find the task. Confirm every `Depends` task is `[x]`. If not, stop and say which one is missing.
2. If the task is `[!]` or lists an unresolved `Q-n` in [README §19.3](README.md#193-unresolved-business-questions-need-your-decision), **stop and ask the user**; do not guess business rules.
3. Set the task to `[~]`.

### Step 1 — Write the task prompt (this is the "great prompt" step)
1. Read the README sections listed in the task's `Refs`, plus any code the task touches.
2. Create `docs/prompts/<TASK-ID>.md` using the [template in §3](#3-task-prompt-template). It must be **specific to this task**: exact files, exact behaviours, exact error codes/status codes, exact test cases — not a restatement of the task title.
3. Run the **prompt quality check** (§3.2). Fix the prompt until it passes.
4. Treat the finished prompt as your work order for the rest of the loop.

### Step 2 — Plan
List the files you will create/change and the order. Prefer the smallest change that satisfies the acceptance criteria. If the plan reveals the task is bigger than ~1 day of work, split it (add `P2-22a`, `P2-22b` to this file) and tell the user.

### Step 3 — Test-first where practical
Write the failing tests that encode the acceptance criteria *before* the implementation (always for domain rules, DB constraints, permission checks, and API contracts). Tests must fail for the right reason first.

### Step 4 — Implement
Follow README conventions: module boundaries (§12.3), SQL-first migrations (§4.3), RFC 9457 errors (§14), money in paise (BR-14), UTC timestamps (BR-15). Never weaken a constraint or test to make something pass.

### Step 5 — Verify (run the gates — do not assume)
Run every gate for the touched area (§5). Paste the actual command output summary. If anything fails: fix it; if it cannot be fixed, set the task `[!]` with the reason and stop.

### Step 6 — Self-review against the prompt
Walk the acceptance criteria one by one; mark each as met with the test that proves it. Re-read your diff for: leaked secrets, missing authorization checks, missing audit logging, missing migration, unhandled error paths, missing OpenAPI annotations.

### Step 7 — Record & tick
1. Fill the task's `Evidence:` line: `date · commands run · result (counts) · commit/ref`.
2. Change `[~]` to `[x]`.
3. Add one line to the [Progress log](#10-progress-log).
4. Refresh the dashboard counts in §8.
5. Report to the user: what changed, what was tested, anything surprising, what's next. **Stop.**

> **Never tick a box on the basis of "it should work."** The tick means the listed tests ran and passed in this working tree.

## 4. Worked example of a generated prompt

*(Illustrative of the expected specificity — for task `P2-22`.)*

````markdown
# P2-22 — Create booking hold (atomic, conflict-free)

## 1. Role
Senior backend engineer (NestJS, PostgreSQL, Kysely).

## 2. Context
- Rento rents individually tracked assets by the hour. A booking = row in `bookings` + row in
  `asset_occupancies` (kind='booking'); conflicts are prevented by the exclusion constraint
  `no_overlapping_occupancy` (README §9.2).
- Read: README §9.1–§9.7, §14.2; `apps/api/db/migrations/0001_*.sql`; `apps/api/src/db/tx.ts`.
- Decided: READ COMMITTED isolation; `FOR UPDATE SKIP LOCKED` candidate selection; SQLSTATE 23P01 → 409.

## 3. Goal
`POST /v1/bookings` creates a 10-minute `held` booking for the first free asset of the requested
model at the requested drawer, or returns 409 `BOOKING_SLOT_TAKEN`. Under any concurrency, two
overlapping bookings for one asset can never both exist.

## 4. Scope
In: validation (duration, granularity, lead time, horizon, hours, closures), idempotency, candidate
selection, insert booking+occupancy, error mapping, OpenAPI.  
Out: payment order creation (P4-01), expiry job (P2-22), notifications (P2-27).

## 5. Detailed requirements
1. Auth: customer JWT required; `401 UNAUTHENTICATED` otherwise.
2. Header `Idempotency-Key` (UUID) required → `422 VALIDATION_FAILED` if missing/malformed.
3. Body `{drawerId, itemModelId, startsAt (ISO-8601 UTC), durationMinutes}`; unknown fields rejected.
4. `durationMinutes` multiple of model `slot_minutes`, within [min,max] → else `422 DURATION_INVALID`.
5. `startsAt` ≥ now+15 min and ≤ now+14 d → else `422 LEAD_TIME_VIOLATION`.
6. Window [starts, ends) must lie inside drawer hours (drawer timezone) and outside closures → else `422 DRAWER_CLOSED`.
7. In one transaction: `SET LOCAL lock_timeout='3s'`; idempotency insert; release expired holds for the window;
   select candidate (README §9.4 step 5); insert booking(`held`, hold_expires_at=now()+10m) and
   occupancy `[starts, ends+buffer)`; on 23P01 rollback to savepoint and try next candidate (max 3).
8. No candidate / all conflict → `409 BOOKING_SLOT_TAKEN`. Lock timeout (55P03) → `503 RETRY_LATER`.
9. Replay with same key+body → `200` same body, no new rows. Same key, different body → `422 IDEMPOTENCY_KEY_REUSED`.
10. Writes `booking_events` (null→held) and an outbox event `booking.held`.

## 6. Files
`apps/api/src/modules/booking/{http/bookings.controller.ts, http/dto/create-booking.dto.ts,
domain/booking-window.ts, data/booking.repository.ts, booking.service.ts}`,
`apps/api/test/booking/create-booking.{unit,db,api}.spec.ts`.

## 7. Acceptance criteria
- [ ] AC-1 …(one per requirement above, each mapped to a test id)

## 8. Test plan (excerpt)
| ID | Level | Scenario | Expected |
|---|---|---|---|
| T-01 | db | Two txs insert overlapping occupancy for same asset concurrently | exactly one commits |
| T-02 | api | 50 parallel requests, 1 asset, overlapping windows | 1×201, 49×409, 0×5xx, 0 overlaps in DB |
| T-03 | api | Adjacent [10,11) then [11,12), buffer 0 | both 201 |
| T-04 | api | Same, buffer 15 → second at 11:00 | 409; at 11:15 → 201 |
| T-05 | api | 2 assets, 2 simultaneous identical requests | both 201, different assets |
| T-06 | api | Replay same key | 200, one booking row |
| T-07 | api | Same key different body | 422 IDEMPOTENCY_KEY_REUSED |
| T-08 | api | Outside hours / during closure / bad duration / too soon / too far | 422 with specific code |
| T-09 | api | No token / other user's replayed key | 401 / independent keys per user |

## 9. Commands
`pnpm --filter api lint && pnpm --filter api typecheck && pnpm --filter api test:unit &&
 pnpm --filter api test:db && pnpm --filter api test:api && pnpm contracts:check`
````

## 5. Definition of Done and quality gates

### 5.1 Global Definition of Done (every task)

1. Acceptance criteria in the task prompt are all met, each proven by a named test.
2. All gates for the touched areas (below) are **green in the current working tree**.
3. No skipped/disabled/`.only` tests added; no lint rules disabled to pass.
4. API change ⇒ OpenAPI regenerated, `pnpm contracts:check` passes, generated clients rebuilt.
5. Schema change ⇒ new forward-only migration (never edit an applied migration), migration tests pass on a fresh DB.
6. Security-relevant change ⇒ authorization + negative tests exist; audit log written for admin mutations.
7. Docs: README/ADR updated if a decision or contract changed; `docs/prompts/<ID>.md` exists.
8. `Evidence:` filled, box ticked, Progress log line added.

## 6. Testing conventions

| Topic | Convention |
|---|---|
| Real DB | DB and API tests run against a **real PostgreSQL+PostGIS container** (Testcontainers) with migrations applied. No mocking the database for anything involving constraints, locking, or geo. |
| Isolation | Each test file gets a clean schema (template database or truncate); tests are order-independent. |
| Time | Inject a `Clock`; never `sleep` to wait for expiry — advance the fake clock or set timestamps explicitly. Fixed dates in the future (e.g. 2030) for bookings. |
| External services | Payments, FCM, email, Google/Meta/Apple verification are **faked at the adapter interface** in CI (local fake JWKS server + signed test tokens; fake Graph API). Real sandboxes only in explicitly named manual/e2e tasks. |
| Auth tests | Every protected endpoint has: no token → 401; valid token without permission/ownership → 403/404; valid → success. |
| Permission tests | A table-driven matrix: for each admin endpoint × {super admin, role with permission, role without, drawer-scoped role outside its drawer}. |
| Concurrency | Real parallel requests (`Promise.all`) against the real app+DB; assertions on both HTTP results **and** direct DB invariants. Re-run ≥5× in CI to catch flakiness. |
| Flutter | Unit (notifiers/repos with `mocktail`), widget (provider overrides, golden optional), integration (against the local stack with seeded data). |
| Admin web | Component tests (Vitest + Testing Library), e2e (Playwright) incl. permission-restricted sessions. |
| Naming | `*.unit.spec.ts`, `*.db.spec.ts`, `*.api.spec.ts`, `*.e2e.spec.ts`, `*.concurrency.spec.ts`; Flutter `*_test.dart`. |
| Flakiness | A flaky test is a bug. Fix the cause; never retry-until-green or skip. |
| Test data | Factories in `apps/api/test/factories`; no shared mutable fixtures. |

## 7. Rules of engagement

1. **One task at a time.** Finish, verify, record, stop.
2. **Evidence or it didn't happen.** Counts and command names, not adjectives.
3. **Don't change the design silently.** If the README is wrong or a better approach appears, propose an ADR update to the user; don't diverge in code.
4. **Business questions are not yours to answer.** Use the README's stated default only when the task says so; otherwise mark `[!]` and ask.
5. **Security defaults:** deny by default; parameterised SQL only; no secrets in code or logs; no precise user coordinates stored or logged.
6. **Migrations are immutable** once merged; fix forward with a new migration.
7. **Small, reviewable commits** (one task = one or a few commits): `feat(P2-22): create booking hold` — body lists tests run.
8. **No scope creep.** Out-of-scope discoveries become new tasks appended to the right phase (with IDs), not silent additions.
9. **Never run destructive commands** (drop DB, force-push, delete data) without explicit user approval.
10. **When blocked or uncertain, stop and report** with what you tried, what you know, and the options.
