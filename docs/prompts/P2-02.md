# P2-02 — Email verification + password reset

## 1. Role
You are a senior backend/security engineer (NestJS, PostgreSQL, Kysely, SMTP) on the Rento platform.

## 2. Context
- Product: time-based rental platform; customers sign in with email+password (P2-01) or social providers (P2-03…06). Email verification gates auto-linking of social accounts (README §15.1, BR-19) and password recovery must not leak which emails have accounts.
- Architecture in play: `apps/api` module `auth-users` (extend), new global `common/mail` module, migration `0003`, config additions, OpenAPI contract + Dart models (the Flutter contract guard from P1-09 fails until every new schema is modelled).
- Relevant README sections: §14.3 (`POST /v1/auth/password/forgot|reset`: "Always 202 on forgot — no account enumeration"), §15 (hashed single-use tokens, generic errors), §8.2 (`users.email_verified_at`, `user_identities.provider_email_verified`), ADR-012.
- Existing code to read first: `src/modules/auth-users/**`, `src/common/clock`, `src/db/{transaction,errors}.ts`, `test/api/auth.api.spec.ts`, `test/support/create-test-app.ts`, `infra/compose.yaml` (Mailpit on 1025/8025), `apps/mobile/lib/core/api/**`.
- Decisions already made (do not revisit): single-use, hashed (SHA-256 of 256-bit random), expiring tokens; time via injected `Clock`; errors via `AppError` → problem+json with **existing** codes only; mail through a `MailSender` interface with an SMTP adapter (Mailpit locally; the production provider is chosen in P0-05).
- Engineering defaults chosen (flag to user): verification link valid 24 h, reset link 1 h; at most one mail per user per purpose per 60 s (cooldown, responses unchanged); invalid/expired/used/superseded token ⇒ `422 VALIDATION_FAILED` on field `token`; reset does **not** sign the user in; a successful reset marks the email verified (the user just proved control of it) and sends a "password changed" notice; only users with a password identity can reset (social-only accounts get 202 but no mail); registration sends the verification mail but does not require verification to sign in.
- Out-of-scope neighbours: transactional outbox / retry of failed mail → P2-23/P2-30 (here mail is sent in the background with errors logged); rate limiting & lockout → P2-31 (only the `@RateLimited('auth')` hook); email change flow → P2-32; real provider/DNS (SPF/DKIM) → P0-05/P4-04; admin invitation mails → P2-11; deep-link/universal-link plumbing in the apps → P3-12.

## 3. Goal
A user can verify their email from a mailed single-use link, and recover a forgotten password through a mailed single-use link that, once used, revokes every session — with identical responses for existing and non-existing accounts, no token ever logged or stored in clear, and mail failures never breaking the request.

**Out of scope**: see §2.

## 5. Detailed requirements
1. **Schema** `auth_tokens(id, user_id → users, purpose ∈ {email_verification, password_reset}, token_hash UNIQUE, email citext NOT NULL, expires_at, used_at, revoked_at, created_at)`; `CHECK (used_at IS NULL OR revoked_at IS NULL)`; index `(user_id, purpose, created_at DESC)`. `email` is the address the token was sent to; a token is valid only while it still equals the user's current email.
2. **Token lifecycle**: issuing a token revokes every earlier unused token of the same user+purpose (`revoked_at`). A token is valid iff `used_at IS NULL AND revoked_at IS NULL AND expires_at > now AND email = users.email AND user.status = 'active'`. Consumption is one atomic conditional `UPDATE … WHERE <valid> RETURNING`, so concurrent uses yield exactly one winner. `created_at` is written from the injected Clock.
3. **`POST /v1/auth/password/forgot`** `{ email }` → **202**, empty body, **always** (unknown, suspended, deleted, social-only, cooled-down, mail failure). Malformed/missing email ⇒ 422 (reveals nothing). When the user is active with a password identity and no mail was sent in the last 60 s: issue token, send reset mail to the user's email. The handler never awaits SMTP (mail is dispatched in the background) so response time does not depend on account existence.
4. **`POST /v1/auth/password/reset`** `{ token, newPassword }` → **204**. Order: look up the token (without consuming); invalid ⇒ 422 `token`; validate `newPassword` with the P2-01 policy against the user's email ⇒ 422 `newPassword` and the token stays **unused**; then, in one transaction: consume the token, replace the Argon2id hash, mark `email_verified_at` (if null) and the identity's `provider_email_verified`, revoke **all** of the user's refresh-token families, revoke the user's other outstanding reset tokens. Afterwards send a "password changed" mail. Access tokens already issued remain valid until they expire (≤ 15 min, ADR-012).
5. **`POST /v1/auth/email/verify`** `{ token }` → **204**: consumes the token, sets `users.email_verified_at = clock.now()` (if null) and `user_identities.provider_email_verified = true` for the password identity. Invalid/expired/used/superseded/email-changed ⇒ 422 `token`.
6. **`POST /v1/auth/email/verification/resend`** (bearer access token) → **202**: if the user is not yet verified and no verification mail was sent in the last 60 s, issues a new token (revoking the old) and sends a mail; otherwise nothing is sent. Missing/invalid access token ⇒ 401.
7. **Registration** (P2-01 endpoint) additionally issues a verification token and sends the mail in the background; registration succeeds even if mail fails.
8. **Mail content**: subject + text + HTML; link `${PUBLIC_WEB_URL}/verify-email?token=<token>` / `/reset-password?token=<token>`; states expiry; "ignore if you did not request this"; HTML-escapes user-supplied values. The "To" is exactly the user's email. No other user's data appears.
9. **MailSender**: `send({ to, subject, text, html })`; `SmtpMailSender` uses nodemailer with 5 s connect / 15 s socket timeouts, `MAIL_FROM`, optional auth, STARTTLS required when `SMTP_SECURE` is false and `NODE_ENV=production`; failures are logged as `warn` with purpose and error class only — never the recipient, link, token or body. Pending background sends are awaited on shutdown.
10. **Logging/storage**: raw tokens exist only in the mail body/link; DB stores hashes; no log line contains a token or a link.
11. **Errors**: only existing codes (`VALIDATION_FAILED`, `UNAUTHENTICATED`); OpenAPI documents the four endpoints.
