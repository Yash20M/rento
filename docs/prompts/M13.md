# M13 — Product photos (fast track: P2-41, P3-34, P3-35)

Owner request (2026-10-18): "admin and the roles who add products in our cupboard should upload images which the user can see in the application".

## Decisions (engineering defaults — flagged)

- **Who**: anyone holding `inventory:write` (the people who maintain the catalogue) — no new permission. Customers and read-only staff cannot upload or remove.
- **Upload**: `POST /v1/admin/item-models/{id}/photos` with the image file itself as the body (`Content-Type: image/jpeg | image/png | image/webp`, at most 5 MB, at most 10 photos per product). The real file signature is checked (the declared type is only a claim); SVG/HTML and every other type are refused — they can carry scripts. `DELETE …/photos/{mediaId}` removes a photo; editing the list through the ordinary product update also frees dropped photos' bytes. Audited (`item_model.photo_added/removed`).
- **Storage**: the `media` table (migration 0015), so backups cover the pictures and the MVP needs no extra service; `ItemPhotoService` hides it, so moving to object storage (S3/R2 + CDN) later changes one class. 5 MB × 10 photos × products is fine at pilot scale; revisit when the catalogue grows.
- **Serving**: `GET /v1/media/{id}` is public (catalogue pictures), `Cache-Control: public, max-age=31536000, immutable`, `ETag` (304 on match), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'`, `Cross-Origin-Resource-Policy: cross-origin` (the web app loads them from another origin).
- **References**: a product's `photos` list holds `/v1/media/<id>` paths (uploaded) or https links (still allowed); both are validated on edit. Clients resolve a path against the API origin.
- **Admin**: Photos gallery inside the product editor (thumbnails, add several files, remove, make cover); changes apply at once. A new product is saved first, then photos are added. **App**: cover photo in the item list, swipeable gallery on the product page, neutral placeholder when there is none or a picture fails to load.
- **Demo data**: the seed generates and uploads a coloured picture for each demo product through the real endpoint.
- Cut (follow-ups): image resizing/thumbnails (the app downloads the original, ≤ 5 MB), drag-and-drop reordering, virus scanning (not needed for sniffed raster formats at this scale), object storage + CDN (Phase 4).

## Tests

API (`m13-photos.api.spec`, 9): upload + public serving with cache/security headers + 304 + audit; JPEG/WebP and ordering; refusals (SVG as PNG, HTML as JPEG, type mismatch, empty, wrong content type, SVG type, > 5 MB) store nothing; 10-photo limit; removal deletes the bytes (404 afterwards, unknown photo 404); list edits accept our paths and https links and refuse http, bad paths, `/etc/passwd`, `javascript:`; permissions (401, customer 403, read-only 403, editor OK, unknown model 404); the public drawer catalogue carries the photos; unknown/malformed media ids 404. Admin (9): gallery order and URLs, upload sends the file with its type, client-side refusal of wrong type / over 5 MB, server refusal shown, remove (uploaded vs link), make cover, save leaves photos alone, 10-photo cap, read-only staff. Flutter (5): URL resolution, cover in the list, placeholder, gallery on the product page, no gallery without photos. Mutations: signature check removed ⇒ P-3 fails, upload permission weakened ⇒ P-7 fails, security header removed ⇒ P-1 fails. Live: real browser shows the demo pictures in the gallery (640 px natural width).
