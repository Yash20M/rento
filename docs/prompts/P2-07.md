# P2-07 — Identity management endpoints

## 1. Role
Senior backend/security engineer (NestJS, PostgreSQL, account-linking) on Rento.

## 2. Context
- README §15.1 rules 6–7 (BR-19): a user may hold several sign-in methods but always ≥ 1; a provider account belongs to one user; linking needs fresh auth. `user_identities` (migration 0002) has `UNIQUE(provider, provider_subject)` and `UNIQUE(user_id, provider)`. P2-03…06 give `SocialAuthService` + three verifiers (disabled provider ⇒ 404).
- Scope per plan: `GET /v1/me/identities`, `POST /v1/me/identities/{google|facebook|apple}` (link), `DELETE /v1/me/identities/{provider}` (provider ∈ password|google|facebook|apple), `PATCH /v1/me` (completes email/phone, and display name). **`GET /v1/me`, `DELETE /v1/me`, suspension blocking = P2-32** (not here); changing an *existing* email = P2-32.
- Decisions (engineering; flagged):
  1. **Fresh auth** = the access token was issued ≤ `FRESH_AUTH_MAX_AGE_SECONDS` ago (default 300, range 30–900; Clock-based). Stale ⇒ `401 TOKEN_EXPIRED` ("recent authentication required") — the same client reaction as an expired token: refresh, retry. Known limit: a refresh mints a fresh token, so this narrows the window for a stolen *access* token but is not a password/OTP step-up; stronger step-up arrives with admin/customer MFA (P4-05). Applies to **link** (as specified); unlink needs only a valid token.
  2. New error code **`IDENTITY_IN_USE`** (409) for "that provider account is already linked to a different user" and "you already have a different account of this provider linked — unlink it first" (README §14.2, catalog and enum together). `ACCOUNT_LINK_REQUIRED` keeps its P2-03 meaning.
  3. Linking the identity the user already has (same provider+subject) is an idempotent 200.
  4. Unlink: not linked ⇒ `404 NOT_FOUND`; last remaining method ⇒ `409 LAST_LOGIN_METHOD`. The check runs under a row lock on the user so two concurrent unlinks can never leave zero methods.
  5. `PATCH /v1/me` `{ name?, phone?, email? }` (≥ 1 field, unknown fields ⇒ 422): `name` 1–100; `phone` E.164 (replace, or `null` not allowed); `email` allowed **only while the account has none** (else 422 on `email`: changing it is P2-32); a new email must not belong to another account (`409 EMAIL_TAKEN`). It is **not written to `users.email` yet**: a verification link bound to that address is mailed (background) and only using it sets `users.email` (+ `email_verified_at`) — so nobody can squat an address they do not own (same reasoning as P2-03). If the address was registered by someone else in the meantime, using the link fails with `409 EMAIL_TAKEN`. Until then the profile still shows `email: null` and `needsProfileCompletion:['email']`. Response: profile `{ id, email, displayName, phone, emailVerified, needsProfileCompletion }`.
  6. All routes need the bearer token and operate on the caller's own rows only; a suspended/deleted account ⇒ `401 UNAUTHENTICATED`. Responses never contain provider subjects, password hashes or tokens.
  7. Linking does not alter `users.email` (use PATCH), but stores the provider email on the identity row.
- Out of scope: `/v1/me` GET/DELETE, suspension, email change (P2-32); rate limiting beyond `@RateLimited` hook (P2-31).

## 3. Goal
A signed-in user can see, add and remove their sign-in methods and complete their profile, with the invariants (≥ 1 method, one owner per provider account, fresh auth on link) enforced server-side and under concurrency.

## 4. Requirements
1. `GET /v1/me/identities` → `[{ provider, email|null, emailVerified, linkedAt }]` ordered by `linkedAt`, caller's rows only.
2. `POST /v1/me/identities/{provider}`: body = the P2-03 per-provider body; verify with the registered verifier (404 if disabled, 401 `SOCIAL_TOKEN_INVALID` if rejected, 503 on provider trouble); fresh-auth check first (before any provider call); then link per decisions 2–3; `provider_email_verified` from the verifier; returns the full identity list (200).
3. `DELETE …/{provider}` → 204 per decision 4; unknown provider path ⇒ 404.
4. `PATCH /v1/me` per decision 5.
5. Concurrency: parallel link of one subject by two users ⇒ exactly one 200, the other 409 `IDENTITY_IN_USE`; parallel unlinks ⇒ at least one method always remains.
6. OpenAPI documents all routes with problem responses; no secrets in logs.

## 5. Test plan (written first)
Api (fake verifiers): I-1 401 without/invalid token on every route; I-2 list shows password only for a password user, then password+google after linking, never another user's rows, no subject in output; I-3 link google to a password user ⇒ 200 list, `provider_email_verified` stored, `users.email` untouched; I-4 stale token (Clock +6 min) ⇒ 401 `TOKEN_EXPIRED` and the verifier is never called; fresh token after refresh ⇒ ok; I-5 subject owned by another user ⇒ 409 `IDENTITY_IN_USE`, nothing changed; I-6 second google subject while one is linked ⇒ 409 `IDENTITY_IN_USE`; I-7 same identity again ⇒ idempotent 200; I-8 invalid token ⇒ 401 `SOCIAL_TOKEN_INVALID`; disabled provider ⇒ 404; I-9 unlink social ⇒ 204 and list shrinks; unlink password when a social exists ⇒ 204 and password login then fails generically; I-10 unlink the only method ⇒ 409 `LAST_LOGIN_METHOD`; not linked ⇒ 404; unknown provider ⇒ 404; I-11 other user's identity cannot be unlinked (404 for provider they don't have, theirs untouched); I-12 two parallel unlinks of a 2-method user ⇒ one 204, one 409, one method left; I-13 two users linking the same subject in parallel ⇒ one 200, one 409; I-14 PATCH: phone/name update; empty body 422; bad phone 422; unknown field 422; email set on a social account with none ⇒ stored unverified + verification mail with a working link; email when one exists ⇒ 422; duplicate email ⇒ 409 `EMAIL_TAKEN`; `needsProfileCompletion` becomes `[]`; I-15 suspended user ⇒ 401; I-16 log capture clean.
