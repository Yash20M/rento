# P1-09 — Dart client generation decision

## 1. Role
You are a senior Flutter/API-contracts engineer evaluating code generation for a Dart client.

## 2. Context
- Product: Rento customer app (Flutter 3.29 / Dart 3.7, Riverpod, dio) and a NestJS API whose OpenAPI document is committed at `packages/contracts/openapi.json` (README §11.5, ADR-010).
- README §11.5 step 3: generate the Dart client with `openapi-generator` `dart-dio`; "evaluate output quality in the spike; fall back to hand-written `freezed` models + contract tests if the generator is painful".
- Existing code to read first: `packages/contracts/openapi.json`, `apps/mobile/lib/core/api/api_client.dart`, `apps/mobile/pubspec.yaml`, `docs/adr/ADR-010-rest-openapi-contract-first.md`.
- Decisions already made (do not revisit): dio as the HTTP layer (P1-08); problem+json → typed errors and interceptors (auth, single-flight refresh, retry, Idempotency-Key) are written by hand in P3-11 regardless of this decision; the TypeScript side is already generated (P1-07).
- Out-of-scope neighbours: interceptors/error mapping (P3-11), repositories and screens (P3-12+), CI wiring (P1-11).

## 3. Goal
A recorded, evidence-based decision between (A) a generated `dart-dio` client and (B) hand-written models + contract tests, with a working, tested, drift-guarded solution in `apps/mobile` and the outcome written into ADR-010.

## 4. Scope
**In scope**: run the generator against the real `openapi.json` in a scratch directory; score it against the criteria below; adopt the winner in `apps/mobile` (generated code committed, or hand-written models); add a unit test that round-trips real sample payloads taken from the OpenAPI examples/schemas; add a drift guard so the Dart side cannot silently diverge from the contract; update ADR-010 (status, decision, evidence).
**Out of scope**: see §2.

## 5. Evaluation criteria (each scored pass/fail, evidence recorded)
G1 The generator runs against our spec without errors. 
G2 The generated package resolves dependencies on Flutter 3.29 / Dart 3.7 (`pub get`). 
G3 Code generation steps (`build_runner`) complete. 
G4 `dart analyze` on the generated code reports no errors. 
G5 Fidelity: required fields non-nullable, nullable fields nullable (`UserSummaryDto.email`, `displayName`), optional `ProblemDetailsDto.errors`, `ErrorCode` as a closed enum with all values, literal-valued properties (`status: 'ok'`, `tokenType: 'Bearer'`) usable, `allOf`-wrapped enum property (`ProblemDetailsDto.code`) typed as the enum. 
G6 Real payloads (register/login/refresh response, a problem+json, `/healthz`) deserialize and re-serialize to equal JSON. 
G7 It works with our own `Dio` instance (so P3-11 interceptors apply) and with a stub adapter. 
G8 Weight and maintainability: extra dependencies, generated file count/size, regeneration is deterministic (two runs identical). 
**Decision rule**: adopt the generated client only if G1–G7 all pass and G8 is acceptable; otherwise adopt hand-written models (B). Either way ADR-010 records the numbers.

## 6. Detailed requirements (for the adopted option)
1. Whichever option is adopted lives under `apps/mobile/lib/core/api/` and exposes: auth request/response models (`RegisterRequest`, `LoginRequest`, `RefreshRequest`, `AuthResponse`, `UserSummary`), `ProblemDetails` + `FieldError`, `ErrorCode`, health models — matching the contract exactly.
2. **Drift guard**: a Dart test (runs in `flutter test`) reads `packages/contracts/openapi.json` and asserts, for every schema the app uses, that field names, requiredness, nullability and enum values equal the Dart models' (via a `toJson`/`fromJson` probe or a declared field table). Changing the contract without updating the Dart models fails this test. If generated, the guard also asserts the committed generated code matches a regeneration (documented command, run in CI only if Java is available).
3. Round-trip tests use the **examples/schemas from the real `openapi.json`**, not invented payloads.
4. No change to the TypeScript contract or the API.

## 7. Acceptance criteria
- [ ] AC-1 G1–G8 evaluated and recorded with evidence. 
- [ ] AC-2 The adopted solution compiles (`flutter analyze` clean) and all existing mobile tests still pass. 
- [ ] AC-3 Round-trip tests on real payloads pass. 
- [ ] AC-4 Drift guard fails when the contract or the Dart model diverges (shown by mutation). 
- [ ] AC-5 ADR-010 updated with the decision; README §19.4 / ADR index status consistent (docs test green).

## 8. Test plan
| ID | Level | Scenario | Expected |
|---|---|---|---|
| R-01 | unit | `AuthResponse` from the contract's example | round-trips equal |
| R-02 | unit | `ProblemDetails` incl. `errors[]` and every `ErrorCode` value | all parse; unknown code handled per design |
| R-03 | unit | `UserSummary` with null email/displayName | parses; serialises nulls |
| R-04 | unit | `/healthz` + `/readyz` models | literal values parse |
| R-05 | unit | missing required field | throws a clear error |
| D-01 | unit | drift guard on the real spec | green |
| D-02 | mutation | rename a field in a copy of the spec / drop an enum value | guard fails |
| C-01 | unit | client call against stub adapter (login) | request path/body/headers correct; response typed |

## 9. Commands
`cd apps/mobile && flutter pub get && flutter analyze && flutter test` · `pnpm verify` · `pnpm contracts:check`. Generator spike (scratch, not committed): `openapi-generator-cli generate -g dart-dio …`.

## 10. Definition of done
Decision recorded with numbers · adopted option tested · drift guard proven by mutation · ADR-010 updated · analyzer clean · Evidence + tick + Progress log + dashboard.

## 11. Stop conditions
Stop and ask if: the generator cannot be downloaded/run on this machine (record G1 as failed-for-environment and fall back to B only with the user's agreement), or the decision would require changing the API contract.
