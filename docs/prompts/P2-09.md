# P2-09 — Roles schema + role CRUD API

## 1. Role
Senior backend/security engineer (NestJS, PostgreSQL, RBAC) on Rento.

## 2. Context
README §13.5 / BR-16..18: roles are data; permissions are the P2-08 code catalog; **Super Admin** is a locked system role holding every permission implicitly. Task: `roles` + `role_permissions`, the locked Super Admin role, and `GET/POST /v1/admin/roles`, `GET/PATCH/DELETE /v1/admin/roles/{id}`, `GET /v1/admin/permissions`.

**Sequencing problem in the plan (and how it is resolved):** the plan wants every call protected by a permission, but the authorization engine (role assignment resolver, cache, `/admin/me`, route enumeration) is P2-12 and assignments are P2-11. Rather than ship open admin routes or block the task, P2-09 adds only the *seam*: the `@RequirePermission('x:y')` decorator, a `PermissionGuard` and a `PermissionResolver` port whose **default implementation grants nothing** (deny-by-default). So in production these routes answer 403 to everyone until P2-11/12 plug in the real resolver; tests plug in a fake resolver to prove the matrix. P2-12 replaces the resolver, adds cache/invalidation, `GET /v1/admin/me` and the route-enumeration test.

Decisions (engineering; flagged):
1. `user_roles` is created here (not P2-11) because "cannot delete an assigned role" needs the FK: `user_roles(user_id, role_id → roles ON DELETE RESTRICT, drawer_id → drawers NULL, granted_by, created_at)`; the RESTRICT FK is the DB guard behind `409 ROLE_IN_USE`. The assignment API, invitations and uniqueness rules stay P2-11.
2. Reads (`GET`) need `roles:read`; create/edit/delete need `roles:manage` (README §13.5 separates them; the plan text says "manage" for all calls). `GET /v1/admin/permissions` needs `roles:read`.
3. Super Admin: seeded by the migration (`is_system`, `is_super_admin`), at most one such row (partial unique index), no `role_permissions` rows allowed (trigger), UPDATE/DELETE of system roles blocked by a trigger (DB-level lock). API edit/delete ⇒ `409 ROLE_LOCKED`. The API cannot create system roles (flags are not accepted from the body).
4. Names unique case-insensitively, trimmed, 1–100 chars; duplicate ⇒ `422 VALIDATION_FAILED` on `name` (no dedicated code exists; flagged). Description ≤ 500 or null.
5. Unknown / duplicate-collapsed permission keys: unknown ⇒ `422` on `permissions`. `PATCH` replaces the permission set when `permissions` is sent, atomically, under a row lock.
6. Starter roles (Operations Manager, Drawer Staff, Support Agent, Viewer) are **not** seeded: their permission sets are an open business question (Q-10).
7. **Not in this task, by plan:** anti-escalation (granter ⊆ own permissions, P2-13) and audit rows for role changes (audit table + interceptor, P2-14). Both are safe to defer because the default resolver denies everyone; they are recorded as requirements on P2-12/13/14.

## 3. Test plan (written first)
DB: seeded Super Admin exists exactly once with flags; second super-admin row rejected; `is_super_admin` without `is_system` rejected; name unique case-insensitively, blank/overlong rejected; role_permissions FK to catalog, PK; permissions on the super-admin role rejected; UPDATE/DELETE of a system role rejected; delete of a role with `user_roles` rejected by FK; deleting a role removes its permission rows.
API (fake resolver): table-driven matrix per route — no token 401, no permission 403 `PERMISSION_DENIED`, `roles:read` can read but not write, `roles:manage` writes, Super Admin all; default resolver ⇒ everyone 403. CRUD happy paths with permissions returned sorted; list includes Super Admin flagged and `assignedCount`; duplicate name (case-insensitive) 422; unknown key 422; empty/odd bodies 422; unknown fields incl. `isSystem` 422; PATCH name/description/permissions (replace) and partial; 404 for unknown id and malformed uuid; edit/delete Super Admin ⇒ 409 `ROLE_LOCKED`; delete assigned ⇒ 409 `ROLE_IN_USE`; delete unassigned ⇒ 204 and permission rows gone; concurrent PATCHes of one role end consistent; concurrent create of the same name ⇒ one 201, one 422; `GET /v1/admin/permissions` returns the P2-08 catalog grouped. Mutations: skip lock check; skip ownership of FK; accept body flags; drop the permission guard.
