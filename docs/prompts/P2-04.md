# P2-04 — Google ID-token verifier

## 1. Role
You are a senior backend/security engineer (NestJS, OIDC/JWT verification with `jose`) on the Rento platform.

## 2. Context
- P2-03 built the social-login core and the `SocialIdentityVerifier` port; no provider is enabled until its verifier is registered (`SOCIAL_VERIFIERS`, default `{}` ⇒ `404`). This task adds the **Google** verifier (README §15.1 table; admin-panel Google sign-in uses the same endpoint with the web client ID as an extra audience).
- Rules from README §15.1 / Google docs: verify the **signature** against Google's public keys (honour `Cache-Control`), `aud` ∈ **our** client IDs (Android, iOS, Web), `iss` ∈ {`accounts.google.com`, `https://accounts.google.com`}, `exp` not passed; key the identity on **`sub`**, never email; read `email` / `email_verified` / `name`. Use a vetted library (`jose`, already a dependency) — no hand-rolled crypto.
- Existing code to read first: `domain/social.ts` (port, `SocialTokenInvalidError`, `SOCIAL_VERIFIERS`), `auth-users.module.ts` (the `{}` provider), `services/access-token.service.ts` (jose usage, Clock), `src/config/app-config.ts`, `common/clock`, `db/errors.ts` (`RetryLaterError`), `test/support/create-test-app.ts`, `docs/adr/ADR-014`.
- Decisions (engineering; flagged): 
  1. Config `GOOGLE_CLIENT_IDS` (comma-separated, trimmed, de-duplicated, optional). The verifier is registered **iff** at least one ID is set; otherwise Google stays `404`. `GOOGLE_JWKS_URL` (default `https://www.googleapis.com/oauth2/v3/certs`) exists so tests can point at a local fake; it must be `https://` in production.
  2. JWKS cache: fetched with `fetch` (5 s timeout), cached until `max-age` from `Cache-Control` (clamped to 60 s … 24 h; 1 h if the header is absent/unparseable), expiry measured with the injected `Clock`. An unknown `kid` triggers **one** refetch, at most once per 30 s (stops an attacker forcing a fetch per request) — this is how key rotation is picked up before `max-age` runs out. If a refresh fails but keys are cached, the stale keys keep working; if there are none, the request fails with `503 RETRY_LATER` (an infrastructure fault is not an invalid token).
  3. Only `RS256` is accepted (Google's algorithm); `alg=none`, HS*, ES* and key-confusion attempts are rejected. Required claims: `sub`, `exp`, `iss`, `aud`. Clock tolerance 10 s.
  4. `email_verified` is true only for boolean `true` or the string `"true"` (Google has sent both); anything else ⇒ unverified. `email` without `sub` is meaningless ⇒ invalid.
  5. Every verification failure maps to `SocialTokenInvalidError` (⇒ `401 SOCIAL_TOKEN_INVALID`); the reason is never returned; logs record only the failure class, never the token.
- Out of scope: Meta (P2-05), Apple (P2-06), link/unlink endpoints (P2-07), admin role gating (P2-11), real Google Cloud client IDs / device checks (P0-02, P3-13, P4-12 manual checklist).

## 3. Goal
`POST /v1/auth/social/google` accepts exactly the ID tokens Google issued for our client IDs, rejects every forgery or misuse with `401 SOCIAL_TOKEN_INVALID`, survives key rotation and a flaky Google endpoint, and is proven against a local fake JWKS server.

## 4. Scope
**In scope**: `GoogleIdentityVerifier` (+ JWKS cache) in `src/modules/auth-users/providers/google/`; config keys; module wiring (`SOCIAL_VERIFIERS` factory); `.env.example`; test support `FakeJwksServer` (real HTTP server + RSA keys + token signing); tests; ADR-014/README notes.
**Out of scope**: see §2.

## 5. Detailed requirements
1. `verify(credentials)` accepts `{provider:'google', idToken}`; any other provider ⇒ `SocialTokenInvalidError`.
2. Success returns `{ provider:'google', subject: sub, email, emailVerified, name }`; `email`/`name` null when absent or not strings.
3. Rejections (all ⇒ `SocialTokenInvalidError`): malformed token, bad signature (right `kid`, wrong key), unknown `kid` after the allowed refetch, `alg=none`, `HS256` signed with the public key bytes, wrong `iss`, wrong `aud` (also when `aud` is another Google client), expired, `nbf` in the future beyond tolerance, missing `sub`, empty `sub`, oversized token (> 8192 chars, before any parsing).
4. Multiple client IDs: a token for any configured ID is accepted; `aud` arrays containing ours are accepted per jose semantics.
5. Cache: second verification within `max-age` ⇒ no second fetch; after `max-age` (Clock advanced) ⇒ refetch; `Cache-Control` `max-age` parsed (also with `public`, `must-revalidate`, uppercase); absent header ⇒ 1 h; clamp bounds enforced.
6. Rotation: Google adds a new key and starts signing with it before the cache expires ⇒ first token with the new `kid` triggers a refetch and verifies. Retired keys disappear after the next refresh. An attacker sending many unknown `kid`s causes ≤ 1 fetch per 30 s.
7. Resilience: JWKS endpoint down/5xx/invalid JSON: with warm cache ⇒ stale keys still verify and the failure is logged (class only); cold ⇒ `RetryLaterError` (503). Concurrent first verifications share one in-flight fetch.
8. Config: `GOOGLE_CLIENT_IDS` parsing, blank ⇒ none, entries must be non-empty strings without whitespace/commas issues; `GOOGLE_JWKS_URL` http(s), https required in production; error messages never echo values.
9. Wiring: with IDs set, `POST /v1/auth/social/google` works end to end (new user / returning / link behaviours already covered by P2-03 tests); with none set ⇒ 404.
10. No token, email or subject appears in logs.
