# M4 — Admin panel (fast track: P3-01, P3-02, P3-03, P3-04, P3-05, P3-06, P3-07 + dashboard + audit viewer)

Goal: a staff member can sign in to the admin panel and run the business through it: see how it is going, manage the catalogue, places, people and roles, and handle bookings — every screen backed by the real API, every action limited by the permissions the server grants.

## Backend additions (small, because the screens need them)
- `GET /v1/admin/dashboard` (`bookings:read`, drawer-scoped): live counts (held / confirmed / active / overdue), the last 7 days (completed, cancelled, no-show, expired, gross paid, refunded — paise) and the next pickups. Time comes from the injected `Clock`.
- `GET /v1/admin/audit-logs` (`audit:read`, unrestricted grant only — the trail is not drawer-scoped, so a drawer-limited grant is refused): newest first, filters entity type/id, actor, action prefix, from/to, cursor paging (`limit` 1–100). This is the lean slice of P2-34 that the audit screen needs; the rest of P2-34 stays open.

## Decisions (engineering defaults — flagged)
- **Session handling (P3-01, demo shortcut)**: the access token lives in memory, the refresh token in `sessionStorage` (cleared when the tab closes). ADR-012's target — refresh token in an `HttpOnly; Secure; SameSite=Strict` cookie with CSRF protection — needs API changes (cookie issuing, CORS/CSRF) and is a hardening follow-up recorded under P3-01; it is not part of the demo. Refresh is single-flight (ADR-012: two simultaneous refreshes of one token revoke the family).
- **Permission-aware UI (P3-02)**: `GET /v1/admin/me` supplies permissions and drawer scopes; menu entries, routes and buttons are hidden/blocked by `can(permission[, drawerId])`. This is a convenience only — the API re-checks every request (deny-by-default), and tests prove a forbidden call is refused by the server, not just hidden.
- **UI stack**: the existing React 19 + Tailwind + TanStack Query + generated typed client; hand-written small components (table, badge, dialog on the native `<dialog>`, form fields) in the style of the existing shadcn-like primitives. No new heavy dependencies.
- **Money** is shown from integer paise (`₹1,234.50`) and entered in rupees with at most two decimals (converted to paise before sending). **Times** are shown in the drawer's own time zone (booking screens) or the browser's (audit), never as raw UTC.
- Staff invitation acceptance (`/accept-invitation?token=…`) is a public page (password sign-up; Google acceptance needs real Google credentials and stays hidden unless configured).
- Not in M4: customer accounts screen (P3-08), reports (P3-09), settings (P3-10), reassign/maintenance/transfers (P2-27/28), service-zone drawing, photo upload.

## Screens
Sign-in · Accept invitation · Dashboard · Bookings (list with filters, detail with history/payment/refund, cancel with reason and optional refund override, hand over, take back) · Inventory: Categories, Item models, Assets · Drawers (details, weekly hours, closures) · Roles (permission matrix, Super Admin read-only) · Staff (list, invite, change roles incl. drawer scope, deactivate, pending invitations) · Audit log.

## Tests
- API: dashboard counts and scope (drawer-limited admin sees only theirs, no token 401, customer 403), audit list (permission, filters, paging, scoped grant refused, secrets absent).
- Admin component tests with a stub API (route-level fetch mock): sign-in success/failure, guard redirect, silent refresh on an expired token (single flight), navigation limited by permissions, forbidden action refused by the server is shown as an error, role matrix create/edit, staff invite, inventory create with server-side validation errors shown on the fields, drawer hours editing, booking cancel with refund override only for `bookings:refund`, dashboard numbers.
- Playwright (M6): the same flows against the real stack.
