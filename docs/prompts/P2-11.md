# P2-11 — Role assignment + admin invitations

## 1. Role
Senior backend/security engineer (NestJS, PostgreSQL, RBAC, account provisioning) on Rento.

## 2. Context
README §13.5 lifecycle: **invite** (email + role(s) + optional drawer scope → single-use, expiring mailed token → invitee sets a password **or** signs in with Google using a *verified* email matching the invitation → assignment becomes active); **promote** an existing customer by assigning a role; **change/revoke** access; "their next admin request is rejected". Builds on P2-09 (`roles`, `user_roles`), P2-10 (`AccountProvisioning`), P2-02 (one-time tokens, mail), P2-03 (Google verification).

Tasks that must be pulled forward (the plan's order makes "deactivation blocks admin API immediately" untestable otherwise):
- **A database-backed `PermissionResolver`** replaces the deny-everyone default: effective permissions = union over the user's roles; any Super Admin role ⇒ `superAdmin`; inactive users get nothing. **Uncached** (every request reads the DB, so changes are immediate). P2-12 adds the short-TTL cache with invalidation, drawer-scope helpers, `GET /v1/admin/me` and the route-enumeration test.
- **Interim anti-escalation, deliberately stricter than the final rules:** every endpoint that can grant power (role create/edit/delete from P2-09, invitations, role assignment, deactivation) additionally requires the caller to be a **Super Admin** (`403 ROLE_ESCALATION` otherwise). Without this, enabling the real resolver would let any `roles:manage` / `admins:manage` holder grant themselves everything. P2-13 replaces it with the README rules (granter's permissions ⊇ granted, only Super Admin grants Super Admin, no self changes, last-Super-Admin protection).

Decisions (engineering; flagged):
1. Reads (`GET admins`, `GET invitations`) need `admins:read`; writes `admins:manage` (+ Super Admin, above).
2. `admin_invitations(email citext, token_hash unique, invited_by, expires_at, accepted_at, revoked_at, accepted_by)` + `admin_invitation_roles(invitation_id, role_id RESTRICT, drawer_id)`; one *open* invitation per email (re-inviting revokes the older one and its link). TTL `ADMIN_INVITATION_TTL_HOURS` (default 168 = 7 days, 1–720).
3. Inviting an email that already has an account ⇒ `409 EMAIL_TAKEN` ("assign roles to the existing account instead"). Accepting when an account with that email appeared meanwhile ⇒ `409 EMAIL_TAKEN` too: attaching roles to an account somebody else may have created and set a password for would be a takeover path. The admin promotes that account directly.
4. Accept (public, rate-limit tagged): `POST /v1/auth/admin-invitations/accept {token, password, name?}` (password policy applies) and `POST /v1/auth/admin-invitations/accept/google {token, idToken}` (Google must report a *verified* email equal to the invitation's, else `409 ACCOUNT_LINK_REQUIRED`-style refusal: `401 SOCIAL_TOKEN_INVALID` for a bad token, `422` on `token`... see tests). Both: consume the invitation atomically (single use), create the account with `email_verified_at = now` (the mailed link proved control), assign the invited roles (`granted_by` = inviter), return the usual `AuthResponse` (signed in). Any unusable token ⇒ the generic `422 VALIDATION_FAILED` on `token`.
5. `PUT /v1/admin/admins/{userId}/roles {roles:[{roleId, drawerId?}]}` **replaces** the user's assignments (empty = remove admin access); target must be an active user; role/drawer ids validated (422). `DELETE /v1/admin/admins/{userId}` = deactivate: removes all assignments, keeps the customer account and its sessions. Both take a user row lock.
6. `GET /v1/admin/admins` lists users holding ≥ 1 role with their assignments; `GET /v1/admin/admins/invitations` lists open invitations; `DELETE /v1/admin/admins/invitations/{id}` revokes one (needed by the UI task P3-04).
7. Invitation mail (text+HTML, role names, expiry, inviter name) goes through the background mail path; failures never break the request.
8. Not here: audit rows (P2-14), cache/`/admin/me`/enumeration (P2-12), final escalation rules (P2-13), admin MFA (P4-05).

## 3. Test plan (written first)
DB (migration 0006): constraints (one open invitation per email, accepted xor revoked, token hash unique, role RESTRICT, duplicate role/scope). Resolver unit/db: union of roles, Super Admin, suspended user, no roles. API: auth/permission matrix incl. Super-Admin-only (403 `ROLE_ESCALATION`); invite → mail with link → accept with password → `AuthResponse` → can call an admin route allowed by the role and not others; expired / used / revoked / superseded / unknown token ⇒ 422 `token`; weak password 422 (link not burnt); Google accept with matching verified email OK, non-matching or unverified refused and nothing created; existing-account email ⇒ 409 on invite and on accept (account appeared meanwhile); promote existing customer by PUT; PUT replace semantics, drawer scope stored, unknown role/drawer 422, suspended target 404/409; deactivation ⇒ the very next admin request is 403; role edit takes effect on the next request; concurrent accepts of one token ⇒ exactly one wins; concurrent invites of one email ⇒ one open invitation; logs contain no token. Mutations: skip single-use, skip email-match for Google, allow accept onto existing account, drop Super-Admin-only, resolver ignoring user status.
