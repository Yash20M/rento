# P2-01 — Email/password auth + tokens

## 1. Role
You are a senior backend/security engineer (NestJS, PostgreSQL, Kysely, JWT) on the Rento platform.

## 2. Context
- Product: time-based rental platform. Customers and staff share one `users` table; staff are users holding roles (P2-09+). Social login (P2-03…06), email verification / password reset (P2-02), rate limiting (P2-31), permissions (P2-12) are separate tasks that build on this one.
- Architecture in play: new module `apps/api/src/modules/auth-users/{http,domain,data}` (README §12.2/§12.3: `http → domain ← data`, domain has no framework/DB imports), migration `0002`, config additions, OpenAPI contract update.
- Relevant README sections: §8.2 (`users`, `user_identities`, `refresh_tokens`), §14.3 (auth endpoints), §14.2 (codes), §15 (Argon2id; JWT 10–15 min with minimal claims; opaque refresh, hashed, rotated, `family_id`, reuse ⇒ family revoked, absolute lifetime 30–60 d, revoked on logout; generic login errors; constant-time compare), BR-19, ADR-012.
- Existing code to read first: `db/migrations/0001_baseline.sql`, `src/db/{transaction,errors,kysely}.ts`, `src/common/clock/*`, `src/common/errors/*`, `src/app.module.ts`, `src/config/app-config.ts`, `test/support/create-test-app.ts`, `test/factories/index.ts`.
- Decisions already made (do not revisit): Argon2id; HS256 JWT access token ~15 min with claims `sub`, `iss`, `aud`, `iat`, `exp`, `jti` only (permissions are resolved server-side, not in the token — ADR-012/013); opaque 256-bit refresh token stored as SHA-256 hash; READ COMMITTED; time via injected `Clock`; errors via `AppError` → problem+json.
- Business rules NOT invented here: no Q-n applies. Engineering defaults chosen (flag to user): password length 10–128 with a small common-password deny-list and no composition rules (NIST-style); refresh absolute lifetime 30 days; strict reuse handling with no grace window; register returns tokens (signs the user in).
- Out-of-scope neighbours: email verification & password reset → P2-02; social login → P2-03…06; `GET/PATCH /v1/me`, identity management → P2-07/P2-32; rate limiting implementation, lockout → P2-31 (only the **hook** is added here); `@RequirePermission`/admin guard → P2-12; suspended-user blocking of already-issued access tokens → P2-32; expired-token cleanup job → P2-23.

## 3. Goal
A customer can register with email+password, sign in, call authenticated endpoints with a short-lived bearer token, rotate sessions with an opaque refresh token whose theft is detected, and sign out — with Argon2id password storage, no secrets in logs/responses, no account-existence leak on login, and stable problem+json errors.

## 4. Scope
**In scope**
- Migration `0002_auth.sql`: `user_identities`, `refresh_tokens`.
- Endpoints: `POST /v1/auth/register`, `/login`, `/refresh`, `/logout`.

- New error code `EMAIL_TAKEN` (409): enum + README §14.2 + `docs/api/error-catalog.md`.
- OpenAPI DTOs and regenerated contract; ADR-012 status note updated.

**Out of scope**: see §2.

## 5. Detailed requirements

### 5.1 Schema (`0002_auth.sql`, forward-only)
1. `user_identities(id uuid pk, user_id uuid NOT NULL → users (plain FK, no cascade), provider text NOT NULL CHECK IN ('password','google','facebook','apple'), provider_subject text NOT NULL, password_hash text, provider_email citext, provider_email_verified boolean NOT NULL DEFAULT false, created_at timestamptz DEFAULT now())`; constraints: `UNIQUE (provider, provider_subject)` (README §8.2), `UNIQUE (user_id, provider)` (one identity per provider per user), `CHECK ((provider = 'password') = (password_hash IS NOT NULL))` named `identity_password_hash_only_for_password`.
2. `refresh_tokens(id uuid pk, user_id → users, family_id uuid NOT NULL, token_hash text NOT NULL UNIQUE, expires_at timestamptz NOT NULL, family_expires_at timestamptz NOT NULL, revoked_at timestamptz, replaced_by uuid → refresh_tokens(id), created_at timestamptz DEFAULT now())`; `CHECK (expires_at <= family_expires_at)`; indexes on `(family_id)` and `(user_id)`.

### 5.2 Passwords
3. Policy (`domain/password-policy.ts`, pure): length 10–128 characters; not in the built-in deny-list of very common passwords (case-insensitive); not equal to the email (case-insensitive); not a single repeated character. Violations are reported together as `errors[{field:'password', message}]` → `422 VALIDATION_FAILED`. No composition rules; Unicode allowed.
4. Hashing: Argon2id via `@node-rs/argon2`, OWASP parameters (memory 19 456 KiB, time 2, parallelism 1), PHC string stored in `user_identities.password_hash`. `verify()` never throws on malformed hashes (returns false).

### 5.3 Endpoints (all JSON; all with `@RateLimited('auth')` metadata)
5. `POST /v1/auth/register` `{ email, password, name, phone? }` → **201** `AuthResponse`. Email trimmed + lower-cased, RFC-format, ≤ 254; `name` 1–100 chars (trimmed) → `users.display_name`; `phone` optional `^\+[1-9]\d{6,14}$`. Unknown fields rejected (422). One transaction: insert `users` (status `active`, `email_verified_at` null) + password identity (`provider_subject` = user id) + first refresh token. Duplicate email (case-insensitive, including concurrent registrations) → **409 `EMAIL_TAKEN`**.
6. `POST /v1/auth/login` `{ email, password }` → **200** `AuthResponse`. Failure for unknown email, wrong password, user without a password identity, or user not `active` → **401 `UNAUTHENTICATED`** with the *same* body detail `"Invalid email or password"` (no enumeration). An unknown email still performs one Argon2 verify against a fixed dummy hash (timing parity).
7. `POST /v1/auth/refresh` `{ refreshToken }` → **200** `AuthResponse` (new access + new refresh, same `family_id`, same `family_expires_at`; the old token gets `revoked_at` and `replaced_by` in the same transaction under `SELECT … FOR UPDATE`). Any failure → **401 `UNAUTHENTICATED`**, detail `"Invalid or expired refresh token"`:
   - unknown token; expired (`expires_at <= now`); user not `active` (family is revoked);
   - **reuse** of an already-rotated token (revoked with `replaced_by` set) ⇒ the **entire family is revoked** and a `warn` security log (family id, user id — never the token) is written;
   - a token revoked by logout (no `replaced_by`) ⇒ 401, no further action.
8. `POST /v1/auth/logout` `{ refreshToken }` → **204**, idempotent: revokes that token's whole family; unknown/already-revoked tokens also yield 204 (nothing leaks). Does not touch other families (other devices).
9. `AuthResponse` = `{ accessToken, refreshToken, tokenType: 'Bearer', expiresIn: <seconds>, user: { id, email, displayName, emailVerified } }`. Never contains hashes.
10. Access token: HS256 JWT, claims `sub` (user id), `iss` `rento-api`, `aud` `rento-clients`, `iat`, `exp = iat + ACCESS_TOKEN_TTL_SECONDS`, `jti` (UUID). Verification enforces algorithm HS256 (rejects `none`/others), issuer, audience, expiry (using the injected `Clock`), signature against `JWT_SECRET` then `JWT_SECRET_PREVIOUS`.
11. `AccessTokenGuard`: reads `Authorization: Bearer <jwt>`; missing/malformed/invalid ⇒ **401 `UNAUTHENTICATED`**; expired ⇒ **401 `TOKEN_EXPIRED`**; on success sets `request.user = { id, tokenId }`. `@CurrentUser()` returns it.
12. Refresh token: 32 random bytes, base64url (43 chars); DB stores only `sha256(token)` hex. Lifetime: `REFRESH_TOKEN_TTL_DAYS` **absolute from the family's first issue** (rotation does not extend it).
13. Logging: no request bodies with credentials, no tokens, no password hashes in any log line (verified by log-capture tests).
