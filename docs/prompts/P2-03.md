# P2-03 — Social login core + linking policy

## 1. Role
You are a senior backend/security engineer (NestJS, PostgreSQL, Kysely, OAuth/OIDC account-linking) on the Rento platform.

## 2. Context
- Product: customers may sign in with Google, Meta (Facebook) or Apple besides email+password (README §15.1, BR-19). The app sends the provider's token; the API verifies it **server-side** and issues its own tokens (ADR-012). This task builds the provider-independent core — the verifier port, account resolution/linking policy, endpoints, tokens — against a **fake verifier**. The real Google / Meta / Apple verifiers are P2-04 / P2-05 / P2-06 and only implement the port.
- Relevant README: §15.1 (flow + linking rules 1–7), BR-19, §14.2/§14.3 (`SOCIAL_TOKEN_INVALID`, `ACCOUNT_LINK_REQUIRED`, `POST /v1/auth/social/{google|facebook|apple}`), §8.2 (`user_identities`), ADR-012, ADR-014.
- Existing code to read first: `src/modules/auth-users/**` (AuthService.startSession/toResult, UserRepository), `db/migrations/0002_auth.sql` (`user_identities` already has the provider check, `UNIQUE(provider, provider_subject)`, `UNIQUE(user_id, provider)`, `provider_email_verified`), `src/db/errors.ts` (UniqueViolationError.constraint), `test/support/create-test-app.ts`, `apps/mobile/lib/core/api/**` + contract guard.
- No new migration is needed (schema from P2-01 is sufficient).
- Decisions made (engineering, within README §15.1 which allows "separate account **or** 409"; flagged to the user):
  1. A new identity whose provider email matches an existing user but **cannot** be auto-linked ⇒ `409 ACCOUNT_LINK_REQUIRED` (a second account with the same email is impossible anyway: `users.email` is unique). "Cannot be auto-linked" = provider says `email_verified=false`, **or** the existing user's email is not verified (rule 5), **or** that user already has a different identity of this provider.
  2. A new identity with a **missing or unverified** provider email creates a user with `users.email = NULL` (the provider email is kept only on the identity, `provider_email_verified=false`) ⇒ `needsProfileCompletion:['email']`. We never store an unverified provider email as the account email — otherwise an attacker could squat a victim's address and block or pre-hijack their registration.
  3. A new identity with a **verified** email and no matching user creates a user with that email and `email_verified_at = now`.
  4. Suspended/deleted users never sign in socially (generic `401 UNAUTHENTICATED`); a verified email matching a non-active user also gives that generic 401.
  5. Phone is not required in the MVP (README Q-1 default), so `needsProfileCompletion` only ever contains `email` today; the `phone` value exists in the contract for when Q-1 changes.
  6. A provider that has no verifier registered (until P2-04…06 land) answers `404 NOT_FOUND`; nothing is half-enabled in production.
- Out of scope: real token verification (P2-04/05/06); link/unlink endpoints `/v1/me/identities` and `LAST_LOGIN_METHOD` (P2-07); profile completion endpoint (P2-07/P2-32); admin Google gating (P2-11); rate limiting beyond the `@RateLimited('auth')` hook (P2-31).

## 3. Goal
`POST /v1/auth/social/{google|facebook|apple}` turns a server-verified provider identity into an Rento session by the linking policy above, never merges accounts on an untrusted email, is safe under concurrent first sign-ins, and is proven with a fake verifier at the adapter interface.

## 4. Scope
**In scope**
- Port: `SocialIdentityVerifier { verify(credentials): Promise<VerifiedSocialIdentity> }`; `VerifiedSocialIdentity { provider, subject, email|null, emailVerified, name|null }`; `SocialTokenInvalidError`; DI token `SOCIAL_VERIFIERS` (`Partial<Record<provider, verifier>>`, empty by default).
- `SocialAuthService.signIn(credentials)` implementing the resolution below; `SocialIdentityRepository`/`UserRepository` additions.
- Three routes (200): `POST /v1/auth/social/google {idToken}`, `/facebook {accessToken}` **or** `{authenticationToken, nonce}`, `/apple {identityToken, nonce, fullName?}`; response = `AuthResponse` + `needsProfileCompletion: ('email'|'phone')[]`.
- OpenAPI regenerated; Dart models (`GoogleLoginRequest`, `FacebookLoginRequest`, `AppleLoginRequest`, `SocialAuthResponse`) + `AuthApi` methods + contract guard; README/ADR-014/catalog notes.
- Test support: `FakeSocialVerifier` (tokens granted per test) and a `socialVerifiers` option in `createTestApp`.

## 5. Detailed requirements
Resolution (one transaction, after verification):
1. `(provider, subject)` exists ⇒ sign in that user (user must be `active`, else generic 401). Nothing else changes (email not overwritten).
2. Else, if `email` present & `emailVerified` and a user with that email exists:
   - user not active ⇒ generic 401;
   - user has `email_verified_at` and has no identity for this provider ⇒ **link** (insert identity, `provider_email_verified=true`), fill `display_name` if empty, sign in;
   - otherwise ⇒ `409 ACCOUNT_LINK_REQUIRED` (nothing written).
3. Else, if `email` present but **not** verified and a user with that email exists ⇒ `409 ACCOUNT_LINK_REQUIRED`.
4. Else create user + identity: email kept only when verified (decision 3), otherwise NULL (decision 2); `display_name` = provider name (Apple: `fullName` from the request body, trimmed, only used if the token carries no name); status active.
5. Concurrency: simultaneous first sign-ins of the same `(provider, subject)` must yield one user; the loser of a `user_identities_provider_subject_key` / `users_email_key` unique violation re-runs the resolution once (so it signs in, links or 409s correctly). Never 500.
6. Response: new session (same token family rules as login), `user.emailVerified` reflects `email_verified_at`; `needsProfileCompletion = ['email']` iff `users.email IS NULL`.
7. Verifier failure (`SocialTokenInvalidError`) ⇒ `401 SOCIAL_TOKEN_INVALID` (generic detail, no provider internals). Unexpected verifier errors ⇒ 500 via the global filter, never leaking the token.
8. Validation: unknown/empty tokens ⇒ 422; Facebook requires exactly one of `accessToken` or (`authenticationToken` + `nonce`).
9. Never log tokens, provider emails or subjects (log `provider` + outcome only).

## 7. Acceptance criteria
- [ ] AC-1 New user created; returning identity signs in without changes → S-1, S-2
- [ ] AC-2 Verified email matching a verified user links; same user signs in afterwards → S-3
- [ ] AC-3 Unverified provider email never links (409 if it matches a user; NULL-email account otherwise) → S-4, S-5, S-6
- [ ] AC-4 Existing user with unverified email never auto-links → S-7
- [ ] AC-5 No email ⇒ `needsProfileCompletion:['email']` → S-8
- [ ] AC-6 One provider subject cannot belong to two users (DB + API) → D-1, S-9
- [ ] AC-7 Concurrency safe → S-10
- [ ] AC-8 Invalid token 401 `SOCIAL_TOKEN_INVALID`; disabled provider 404; suspended 401 → S-11…S-13
- [ ] AC-9 No secrets in logs; contract + Dart + docs consistent → S-14, gates
