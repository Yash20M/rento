# M3 — Booking core (fast track: P2-15, P2-22, P2-23, P2-24, M3-pay, P2-26-lite)

Goal: a signed-in customer can hold a slot, pay (fake gateway), get a confirmed booking and cancel it with a refund; staff can hand the item over and take it back; nobody can ever double-book an asset. Builds on M2 (catalog, availability) and M1 (permissions, audit).

## Decisions (engineering defaults — flagged, owner decisions still open)
- **Idempotency (P2-15)**: `Idempotency-Key` (8–128 chars) required on `POST /v1/bookings`. Claim row in its own short transaction; the booking and the stored response are committed in ONE transaction, so a crash can never leave a booking without its replay record. Same key + same request hash ⇒ stored response replayed (`200`, `Idempotency-Replayed: true`); still running ⇒ `409 REQUEST_IN_PROGRESS`; other body ⇒ `422 IDEMPOTENCY_KEY_REUSED`; keys are per user; a failed attempt deletes its claim so the client can retry with the same key; claims older than 2 minutes that never completed are reclaimed; completed keys older than 24 h are swept.
- **Hold (P2-22)** per README §9.4 and **ADR-015** (locked-asset policy). Rules: model active and offered at the drawer (else 404); drawer `active` and the whole window inside ONE local day's opening hours and outside closures (else `DRAWER_CLOSED`); duration a multiple of the slot within [min, max] (else `DURATION_INVALID`); start ≥ now + `BOOKING_MIN_LEAD_MINUTES` (15) and ≤ now + `BOOKING_MAX_ADVANCE_DAYS` (90, same as availability) else `LEAD_TIME_VIOLATION`. Price = slots × `price_per_slot_paise`; the amount to pay = price + deposit (placeholder, Q-3). Hold lasts `HOLD_MINUTES` (10). Writes `bookings`, `asset_occupancies` `[start, end+buffer)`, `booking_events`, outbox `booking.held`. Expired holds in the way are released first (lazy cleanup).
- **Expiry + outbox (P2-23)**: `HoldSweeper.expireDue` (SKIP LOCKED batches, idempotent) sets `expired`, releases the occupancy, event + outbox; a small outbox dispatcher marks events delivered (handlers are the notification skeleton, P2-30). Runs every `JOBS_INTERVAL_SECONDS` (30) inside the API process; two instances are safe (SKIP LOCKED). pg-boss is NOT added for the demo (ADR-007 still applies for later scale-out).
- **Pay (M3-pay)**: `PaymentProvider` interface + in-process `FakePaymentProvider` (HMAC signature). `POST /v1/bookings/{id}/payment` creates (or returns) the order, `POST …/payment/confirm {orderId, paymentId, signature}` verifies server-side and confirms; `POST …/payment/simulate` (fake provider only) plays the part of the checkout screen and returns the three values. Confirmation of a hold that already ran out re-takes the slot if it is still free (the constraint decides), otherwise `410 HOLD_EXPIRED` and nothing is captured (README §9.5).
- **Cancel + refund (P2-24)**: owner cancels `held`/`confirmed` (idempotent: already cancelled ⇒ 200 same state); `active`/`overdue`/terminal ⇒ `409 INVALID_STATE`. Refund = tier percent (env `REFUND_TIERS`, placeholder 100 % ≥ 24 h, 50 % ≥ 2 h, 0 % below, Q-5) of the rental price + the full deposit, computed from time-to-start; one `refunds` row (unique per booking), processed through the provider. Admin cancel: `bookings:cancel`, mandatory reason, optional `refundPercent` override needs `bookings:refund`; audited.
- **Staff lite (P2-26-lite)**: `bookings:write` — pickup (`confirmed` → `active`, from `PICKUP_EARLY_MINUTES` before the start until the end) and return (`active`/`overdue` → `completed`, occupancy shrinks to now + buffer when early; no early-return refund, Q-6). Sweeper also marks `active` past the end as `overdue` and `confirmed` not picked up `NO_SHOW_GRACE_MINUTES` after the start as `no_show` (occupancy released, no refund). Pickup codes, late fees, extension are NOT in M3 (P2-25/P2-26 stay open).
- **Reads**: customer `GET /v1/bookings`, `GET /v1/bookings/{id}` (other users' ⇒ 404); admin `GET /v1/admin/bookings` (filters status/drawer/date/text, cursor), `GET /v1/admin/bookings/{id}` with history, payment, refund — drawer-scoped (`bookings:read`).
- New error codes: `INVALID_STATE` (409), `PAYMENT_INVALID` (422). New migration `0009_booking_engine` (idempotency_keys, booking_events append-only, outbox_events, payments, refunds).

## Tests (real PostgreSQL, fake clock)
DB: constraints of 0009 (append-only history, one open payment and one refund per booking, idempotency completeness). Unit: refund tiers at the boundaries, state-machine table, booking window rules, request hash. API (`m3-bookings.api.spec`): validation table, permission matrix, idempotency replay / reuse / concurrent same key / other user, every rule above, double-booking attempts, buffer, maintenance and inactive assets excluded, other user's booking 404, pay → confirm → cancel → refund amounts, late payment, expiry sweep, admin scope and audit rows. Concurrency (`booking-api.concurrency.spec`): 30 parallel identical requests on one asset ⇒ exactly one 201 and 29 × 409; pool of 3; different slots on one unit all succeed (ADR-015); cancel then rebook; invariant query after each. Mutation checks: idempotency ignores the body, refund tier off by one, cancel not releasing the occupancy, ownership check removed.
