# P1-07 — OpenAPI generation + contract drift check

## 1. Role
You are a senior TypeScript/API-contracts engineer (NestJS Swagger, openapi-typescript) on the Rento platform.

## 2. Context
- Product: time-based rental platform; clients are a Flutter app and a React admin SPA that both consume the same REST API.
- Architecture in play: `apps/api` (source of truth, decorators → OpenAPI), `packages/contracts` (committed `openapi.json` + generated TS types + thin typed client), root `pnpm contracts:*` scripts.
- Relevant README sections: §11.5 (generate `openapi.json` from decorators; commit under `packages/contracts`; **CI fails if regenerating produces a diff**; TS client via `openapi-typescript`; Dart decided in P1-09), §14.1 (OpenAPI 3 generated from code, `/docs` non-prod, committed to `packages/contracts`), §14.2 (problem+json error shape).
- Existing code to read first: `apps/api/src/{openapi.ts,bootstrap.ts,main.ts}`, `apps/api/src/common/health/health.controller.ts`, `packages/contracts/*`, root `package.json`.
- Decisions already made (do not revisit): `openapi-typescript` for types; DTO classes + `@nestjs/swagger` decorators (no Nest CLI plugin); REST under `/v1`, health outside it.
- Out-of-scope neighbours: Dart client / ADR-010 → P1-09; admin SPA wiring of the client → P1-10; CI workflow that runs `contracts:check` → P1-11; business endpoints and their DTOs → P2.

## 3. Goal
`pnpm contracts:generate` regenerates `packages/contracts/openapi.json` and the TypeScript types from the real Nest app; `pnpm contracts:check` fails if either committed artefact differs from what the code produces, or if the typed client does not compile. API responses and the RFC 9457 error shape are described precisely enough that clients get real types, not `unknown`.

## 4. Scope
**In scope**
- `apps/api/src/openapi-export.ts` — boots the app **without listening and without a database connection**, builds the document exactly as `/docs-json` does, writes deterministic JSON (2-space indent, trailing newline) to the path given as `argv[2]`.
- Response DTOs with `@ApiProperty`: `HealthResponseDto`, `ReadinessResponseDto`, `ProblemDetailsDto` (+ `FieldErrorDto`); health controller documents `200` and `503` (`application/problem+json`) with them.
- `packages/contracts`: `openapi.json` (committed), `src/generated/schema.d.ts` (generated by `openapi-typescript`, committed), `src/index.ts` exporting `paths`, `components`, `createApiClient(baseUrl, options?)` built on `openapi-fetch`, a compile-time usage file asserting real response types, scripts and a vitest suite.
- Scripts: `contracts:generate`, `contracts:check` (root, delegating to `packages/contracts/scripts/contracts.mjs`).

**Out of scope**: see §2.

## 5. Detailed requirements
1. **Export** is deterministic: running it twice yields byte-identical files; it needs no env vars (uses an inert config with an unreachable DB URL and silent logs) and never opens a DB connection (lazy pool, closed on shutdown).
2. **DTOs**: `HealthResponseDto { status: 'ok' }`; `ReadinessResponseDto { status: 'ready'; checks: { database: 'up' } }`; `ProblemDetailsDto { type: string; title: string; status: number; code: string(enum of ErrorCode); detail: string; errors?: FieldErrorDto[]; traceId: string }`; `FieldErrorDto { field: string; message: string }`. `code` is documented as an enum of every `ErrorCode`.
3. **Health docs**: `GET /healthz` → `200 HealthResponseDto`; `GET /readyz` → `200 ReadinessResponseDto`, `503 ProblemDetailsDto` with media type `application/problem+json`.
4. **Generate** (`contracts.mjs generate`): build API → export spec to `packages/contracts/openapi.json` → run `openapi-typescript` to `packages/contracts/src/generated/schema.d.ts`.
5. **Check** (`contracts.mjs check`), exit 1 with a readable message on any failure:
   a. regenerate spec and types into a temp dir and compare byte-for-byte with the committed files (drift guard); message names the drifted file and says to run `pnpm contracts:generate`;
   b. the spec is valid OpenAPI 3 (`openapi` starts with `3.`, has `paths`, every `$ref` resolves — validated by `openapi-typescript` succeeding);
   c. `tsc --noEmit` in `packages/contracts` passes (client + usage assertions compile).
   Options (used by tests): `--spec <file>` and `--types <file>` select the committed files to compare against; default is the real ones.
6. **Client**: `createApiClient(baseUrl, { fetch? })` returns an `openapi-fetch` client typed with `paths`; no auth logic yet (P1-10).
7. **Compile-time assertions** (`src/usage-check.ts`, excluded from the package entry): `GET /healthz` data is `{ status: 'ok' }`; `GET /readyz` error is `ProblemDetails`-shaped with `code` typed as the enum union; wrong path is a type error (`@ts-expect-error`).
8. Generated files are excluded from ESLint/Prettier (already `**/generated/**`) and carry no timestamps.

## 6. Files to create / modify
Create: `apps/api/src/openapi-export.ts`, `apps/api/src/common/health/health.dto.ts`, `apps/api/src/common/errors/problem.dto.ts`, `packages/contracts/{openapi.json, scripts/contracts.mjs, src/index.ts, src/usage-check.ts, src/generated/schema.d.ts, vitest.config.ts, test/contracts.spec.ts}`.
Modify: `apps/api/src/common/health/health.controller.ts`, `packages/contracts/{package.json,tsconfig.json}`, root `package.json` (scripts), `DEVELOPMENT_PLAN.md`.

## 7. Acceptance criteria
- [ ] AC-1 Export is deterministic and DB-free. → T-01, T-02
- [ ] AC-2 Spec documents health + problem+json with real schemas (no `unknown` responses). → T-03, T-04
- [ ] AC-3 `contracts:check` passes on a clean tree. → T-05
- [ ] AC-4 Drift in the spec (tampered/outdated `openapi.json`) fails the check. → T-06
- [ ] AC-5 Drift in the generated types fails the check. → T-07
- [ ] AC-6 A real source change without regenerating fails; regenerating fixes it. → M-01
- [ ] AC-7 A client that no longer compiles fails the check. → T-08
- [ ] AC-8 Client works at runtime (URL, parsing) against a stub `fetch`. → T-09
- [ ] AC-9 `ErrorCode` enum in the spec equals the API's `ErrorCode` list. → T-10
