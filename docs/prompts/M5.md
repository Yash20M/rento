# M5 — Mobile app (fast track: P3-11, P3-12, P3-14, P3-15, P3-16, P3-17, P3-18, P3-19)

Goal: a customer can sign in, find a nearby drawer, pick an item and a time, hold the slot, pay (demo gateway), see the booking and cancel it — against the real backend.

## Decisions (engineering defaults — flagged)

- **Session (P3-11)**: access token in memory only, refresh token in secure storage; `AuthInterceptor` adds the bearer and refreshes **once** (single flight, ADR-012) and repeats the call; a refused refresh ends the session; an expired-looking repeat is never refreshed twice (no loop). `ApiException` carries the stable error `code` (unknown codes degrade to `unknown`); screens branch on codes, never on text.
- **Auth (P3-12, lean)**: email + password sign-in and registration with the server's field messages; **no** password-reset/verify screens and **no** Google/Meta/Apple buttons yet (they need real app IDs — Phase 0); sign-out.
- **Location (P3-14, lean)**: "Use my location" (browser/OS permission, every refusal explained with a way forward), demo places on non-production flavors, typed coordinates (range-checked). The position is held in memory for the session only, sent for the search and never stored or logged (README §10.6).
- **Browse (P3-15/16)**: nearest open drawers with distance, close-but-closed/out-of-stock ones listed separately with the reason; drawer page (address, open now, hours, pickup instructions, items with price and free units).
- **Slot picker (P3-17)**: 7 days from "today" in the DRAWER's calendar, start times in the DRAWER's time zone (`timezone` package; the phone's zone is never used), lengths = multiples of the slot within the model limit and what some unit can still do from that start; price in integer paise with the deposit shown separately; availability explained as a snapshot.
- **Booking (P3-18)**: one random UUID `Idempotency-Key` per attempt, reused when the SAME attempt is retried after a transient failure (network/503/in-progress) and replaced after a definite answer (409/422) or any change of choice; holds shown with a countdown from an injectable clock; pay = create order → (demo) checkout → signed confirmation verified by the server — the app never marks anything paid itself; 410/422 explained; "release this slot" cancels the hold.
- **My bookings (P3-19, lean)**: upcoming/past lists, detail with price split, payment and refund, cancel with confirmation (shows the refund the server computed); **no** extend (P2-25) yet.
- **Web demo**: the app runs in Chrome (`flutter run -d chrome`); the API therefore gained an explicit CORS allow-list (`CORS_ALLOWED_ORIGINS`, exact origins, no credentials, default none).
- Strings live in `app_en.arb` (generated l10n); money/time helpers are pure and tested.

## Tests
Unit: interceptor (9 cases incl. single-flight, no loop, body/key preserved on repeat), models vs the OpenAPI contract (Dart contract guard extended to the customer-facing schemas), `ApiException`, UUID, money, time zones (India, London summer, New York), slot lengths, routing redirects. Widget flows against a stub API: sign-in/registration/sign-out, location (every refusal), nearby/unavailable/out-of-area, drawer → slots → reserve (key behaviour), payment success/failure/expiry, my bookings and cancel. API: CORS (`cors.api.spec`). Real stack: `pnpm demo:smoke` (headless browser drives the Flutter web app and the admin panel).

Gates: `pnpm verify` (16) at the end of the milestone.
