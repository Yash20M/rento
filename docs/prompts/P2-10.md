# P2-10 — Super Admin bootstrap CLI

Role: senior backend/security engineer. Context: README §13.5 — the first Super Admin is created only by a server-side CLI, never the public API; P2-09 seeded the locked *Super Admin* role and `user_roles`.

Behaviour: `pnpm --filter api cli bootstrap-super-admin --email … [--name …] [--force-additional]`. One transaction under an advisory lock: create the account (password-less) or promote the existing active one, assign the locked role, and — only if the account has no password — issue a single-use, hashed, expiring setup link (the P2-02 password-reset token; `setPasswordHash` creates the password identity when absent). Refuse when an *active* Super Admin exists unless `--force-additional`; same email again = no-op; suspended/deleted accounts refused; exit codes 0 / 1 (refused or failed) / 2 (usage). No password option, nothing but the link is printed, connection strings never printed.

Tests: unit (parser, formatter), db (all rules above, concurrency, rollback), api (real built CLI as a child process; link sets the first password end to end; no HTTP route/body can create or flag a Super Admin). Mutations: remove refusal, advisory lock, link issuing, identity creation.

Out of scope: audit rows (P2-14), invitations (P2-11), anti-escalation (P2-13).
