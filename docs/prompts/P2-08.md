# P2-08 — Permission catalog

## 1. Role
Senior backend engineer (NestJS, PostgreSQL, RBAC) on Rento.

## 2. Context
README §13.5 / BR-16..18: permissions are **code** (a fixed `resource:action` catalog), roles are **data** (P2-09). A `permissions` table seeded by migration holds the catalog so `role_permissions` can reference it by FK. "A startup/CI check fails if the code and the `permissions` table drift." Super Admin implicitly holds all permissions (no rows). This task builds only the catalog; roles tables/CRUD = P2-09, the guard/decorator = P2-12, `GET /v1/admin/permissions` = P2-09.

Decisions (engineering; flagged):
1. 21 keys exactly as in the README §13.5 table (Inventory 2, Assets 3, Drawers 2, Bookings 4, Customers 2, Reports & audit 2, Settings 2, Access control 4). Key format `^[a-z_]+:[a-z_]+$`, enforced in code, by a DB CHECK, and by tests.
2. Migration `0004_permissions.sql` creates `permissions(key PK, group_name, description, created_at)` and inserts the catalog. Future permissions arrive as new forward-only migrations (never edit 0004).
3. **Startup check** (`onApplicationBootstrap`): a key in code but missing from the DB ⇒ **boot fails** naming the keys (a route would enforce a permission no role could ever hold). A key in the DB but not in code ⇒ **warning only** (a rolled-back deploy runs old code against a newer schema; crashing would turn a rollback into an outage). If the database is unreachable the check is skipped with a warning — `/readyz` already reports that, and the check runs again on the next start. CI is strict both ways (DB test).
4. The code catalog is exported (`PERMISSIONS`, `PermissionKey`, `isPermissionKey`, `permissionsByGroup()`) as the source for the later catalog endpoint and guard typing.
5. Doc drift: a unit test parses the README §13.5 table and fails if it and the code disagree.

## 3. Test plan (written first)
Unit: key format/uniqueness/non-empty descriptions/count, README table ⇔ code, `isPermissionKey`, grouping; `diffCatalog` (missing/unknown); service: missing ⇒ throws naming keys, unknown ⇒ warns not throws, clean ⇒ silent, DB error ⇒ warns not throws. DB (real PostgreSQL): migrated table ⇔ code in both directions; CHECK rejects bad keys (`Bad:Key`, `nocolon`, `a:b:c`, `a:`, `:b`, empty, upper case, digits); PK uniqueness; empty description rejected. API: app boots on a migrated DB; deleting a catalog row ⇒ app init fails naming the key; an extra DB row ⇒ boots and warns. Mutations: drop a key from code ⇒ README/db tests fail; drop the DB check; swallow the missing-key error.
