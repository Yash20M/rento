# M9 — Payment gateway: Razorpay adapter + webhooks (fast track: P2-39)

Owner request (2026-10-18): "for razorpay for now we don't have keys — make a demo thing for it". The demo gateway stays the default; the real adapter is built now and proven against a local fake of Razorpay's HTTP API, so switching on real payments later is configuration plus a sandbox checklist (P4-01…03), not new code.

## Decisions (engineering defaults — flagged)

- `PAYMENT_PROVIDER=fake|razorpay` (default `fake`). `razorpay` refuses to start without `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`; `RAZORPAY_BASE_URL` exists only so tests can point at a local fake.
- Orders are created with **manual capture** (`payment_capture: 0`): the customer's payment is only authorised; the server captures after verifying the checkout signature (`HMAC-SHA256(order_id|payment_id, key_secret)`), so a booking that cannot be confirmed never takes money. Refunds carry the refund id as `receipt` (stable per booking).
- **Webhook** `POST /v1/payments/webhooks/razorpay` is the safety net for a customer who paid but whose app never called "confirm". Signature = `HMAC-SHA256(raw body, webhook secret)` over the **raw bytes** (Nest `rawBody`), constant-time compared, checked before the JSON is parsed or trusted (401 otherwise). Each event id is recorded once (`webhook_events`, migration 0012) and processed once. Only `payment.authorized` changes state: it confirms the hold through the same code path as the customer's own confirmation (late payment on an expired hold re-takes the slot only if it is free); a cancelled booking or a lost slot is acknowledged and **not captured**. `payment.captured`, `order.paid`, `payment.failed`, refund events are recorded and ignored (this API's own calls already wrote those results). A gateway failure during capture rolls everything back **including the event record**, so the gateway's redelivery can try again.
- The demo checkout in the app became a "Razorpay checkout (demo)" sheet with a succeeding test card, a succeeding UPI id and a declining test card (the slot stays held; the customer can retry).
- Assumptions to confirm against the Razorpay sandbox (no keys existed): endpoint paths/fields as documented publicly, `X-Razorpay-Signature` header name, event payload shape (`payload.payment.entity.{id,order_id}`), webhook retry behaviour.
- Cut (follow-up): extension payments via webhook (the app's own confirmation drives them), Razorpay Checkout SDK in the app (needs the key), webhook reconciliation report.

## Tests

Unit (7): request shape (paise, manual capture, basic auth), signature vectors (good/tampered/foreign secret), capture and refund calls, gateway errors never echo the response body, config rules. API (12, `m9-razorpay.api.spec` against a local fake Razorpay HTTP server): order creation, demo `simulate` endpoint disabled with a real gateway, checkout verification + capture, refund through the gateway; webhook confirms once and a redelivery does nothing, missing/wrong/foreign/tampered signature ⇒ 401 and nothing stored or captured, non-events refused, ignored event types, cancelled booking not captured, late payment on a free slot, capture failure ⇒ nothing confirmed and retry succeeds, six parallel deliveries ⇒ one capture. Flutter: declined test card keeps the hold and allows retry. Mutations: signature check removed ⇒ W-2 fails; event dedupe removed ⇒ W-1 fails.
