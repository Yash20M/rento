# P2-06 — Sign in with Apple verifier

## 1. Role
Senior backend/security engineer (NestJS, OIDC/JWT with `jose`) on Rento.

## 2. Context
- P2-03 core + P2-04/05 verifiers exist; the shared JWKS cache is `providers/shared/jwks-cache.ts`. This adds **Apple** (README §15.1; App Store guideline 4.8 makes it mandatory on iOS once Google/Meta are offered).
- Apple facts (discovery document checked 2026-10-16): issuer `https://appleid.apple.com`, keys at `https://appleid.apple.com/auth/keys`, RS256. `aud` is the app's bundle ID (native) or a Services ID (web). Claims: `sub` (stable per team+user), `email`, `email_verified` (boolean or `"true"`), `is_private_email` (private relay), `nonce`. Apple delivers the user's **name only on the first authorization, outside the token** — the app forwards it as `fullName` (already handled by P2-03 on first account creation only).
- Decisions (engineering; flagged): (1) Enabled iff `APPLE_CLIENT_IDS` (comma list: bundle ID, plus Services ID if the web uses it) is set; else 404. `APPLE_JWKS_URL` overridable, https in production. (2) Nonce: the app sends the **raw** nonce; Apple's token carries either that value or its SHA-256 hex (depends on the client library) — we accept `claim === raw` or `claim === sha256hex(raw)`; anything else, or no nonce claim, is invalid. (3) Apple `email_verified` true ⇒ trusted (Apple is authoritative, incl. private-relay addresses, which are deliverable); `email` without verified flag ⇒ unverified. (4) Same hardening as Google: RS256 only, 10 s tolerance, required `sub exp iss aud nonce`, size bounds, errors ⇒ `SocialTokenInvalidError`, key-endpoint trouble ⇒ 503 via the shared cache.
- Out of scope: Apple "client secret"/revocation/server-to-server notifications (Phase 4), real Apple Developer setup (P0-04), identity endpoints (P2-07).

## 3. Goal
`POST /v1/auth/social/apple` accepts exactly identity tokens issued for our bundle/service IDs with the right nonce, stores private-relay emails like any verified email, captures the name once, and rejects everything else with `401 SOCIAL_TOKEN_INVALID`.

## 4. Test plan (written first)
Unit (`FakeJwksServer`): A-1 valid ⇒ identity (sub/email/verified/name null); A-2 `email_verified` true/"true"/false/missing and relay flag ⇒ verified only for true/"true"; A-3 relay address accepted; A-4 nonce raw ok, nonce sha256-hex ok, wrong/missing/claim-missing rejected; A-5 wrong aud (incl. another Apple app), second configured ID ok; A-6 wrong/lookalike iss; A-7 expired/nbf; A-8 forged (unpublished key, tampered, `alg=none`, HS256 confusion); A-9 missing/empty `sub`, garbage, oversized token/nonce (no fetch); A-10 other provider's credentials; A-11 key endpoint down cold ⇒ 503; A-12 logs clean; config U-4: ids parse/dedupe, JWKS URL rules. API end to end (config → verifier → endpoint): P-1 new user with relay email stored as verified account email and `needsProfileCompletion:[]`; P-2 fullName used once; P-3 verified Apple email equal to a verified password user links; to an unverified-email user ⇒ 409; P-4 wrong nonce/aud/expired ⇒ 401; P-5 unset ⇒ 404; P-6 logs clean. Mutations: skip nonce check; skip aud; accept any nonce claim missing; treat unverified email as verified; skip issuer.
