# P1-12 — ADRs & API conventions docs

## 1. Role
You are a senior engineer/technical writer on the Rento platform, writing for engineers who will join later and must understand *why* the system is the way it is.

## 2. Context
- Product: time-based rental platform (Flutter app, React admin, NestJS API, PostgreSQL/PostGIS).
- Architecture in play: documentation only (`docs/adr/`, `docs/api/`) plus one consistency test in `apps/api/test/unit`.
- Relevant README sections: §19.4 (ADR summary table; "each ADR becomes a short file in `docs/adr/` in Phase 1"), §14.1 (conventions), §14.2 (error codes), and the sections each ADR summarises (§4.1–§4.5, §6.1, §9, §10, §11.5, §13.5, §15, §15.1).
- Existing code to read first: `docs/adr/ADR-005-sql-first-migrations.md` (format), `apps/api/src/common/errors/{error-codes.ts,problem.ts}`, `apps/api/src/db/errors.ts`, README §14, §19.4.
- Decisions already made (do not revisit): the 14 decisions in README §19.4. This task records them; it does not change them.
- Out-of-scope neighbours: the locked-asset-policy ADR (decided in P2-22) and the Dart-client ADR outcome (P1-09) — only mentioned as pending.

## 3. Goal
A new engineer can read `docs/adr/` and `docs/api/` and learn each decision, its trade-offs, and its evidence; the docs cannot silently drift from the code or the README because a test checks them.

## 4. Scope
**In scope**: ADR-001…ADR-014 (ADR-005 already written in P1-04), `docs/adr/README.md` index, `docs/api/conventions.md`, `docs/api/error-catalog.md`, README §19.4 table updated with links/statuses, test `docs.unit.spec.ts`.
**Out of scope**: new decisions; implementing any planned convention (pagination, idempotency, auth, rate limiting).

## 5. Detailed requirements
1. Each ADR file `docs/adr/ADR-NNN-<slug>.md`: title `# ADR-NNN — …`; a header table with **Status** (`Accepted (date)` or `Proposed`) and **Related**; sections Context, Decision, Consequences, Evidence or a "Status note" saying what makes a Proposed ADR Accepted; Alternatives where the README compares options.
2. **Status policy**: *Accepted* only if the decision is implemented and covered by passing tests (001–005, 009 today); everything else *Proposed* with the condition for acceptance. ADR-010 stays Proposed until P1-09 records the Dart outcome.
3. README §19.4 table: each ADR id links to its file; the Status column equals the file's status word (`Accepted`/`Proposed`).
4. `docs/api/error-catalog.md`: one row per `ErrorCode` (HTTP status, code, client meaning, raising task) plus the thrown-value → problem mapping table; states that a code is added in three places (enum, README §14.2, catalog).
5. `docs/api/conventions.md`: rules from README §14.1, each marked implemented or planned (with task); contract workflow; new-endpoint checklist.
6. **Consistency test** (`apps/api/test/unit/docs.unit.spec.ts`):
   - catalog codes == `ErrorCode` values == codes in README §14.2 (no extras either way; no duplicates in the catalog);
   - catalog HTTP status matches the real status of `SlotTakenError` (409) and `RetryLaterError` (503);
   - every ADR 001…014 file exists exactly once, heading number matches filename, required sections present, Status word valid;
   - README §19.4 rows ↔ files: same ids, same statuses, working relative link targets;
   - `docs/adr/README.md` index table lists all 14 with matching statuses;
   - every relative markdown link in `docs/adr/*.md` and `docs/api/*.md` resolves to an existing file.

## 6. Files
Create: `docs/adr/ADR-001…014 (except 005)`, `docs/adr/README.md`, `docs/api/{conventions.md,error-catalog.md}`, `apps/api/test/unit/docs.unit.spec.ts`. Modify: `README.md` §19.4, `DEVELOPMENT_PLAN.md`.
