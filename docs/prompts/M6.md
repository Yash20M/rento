# M6 — Demo packaging (fast track: P3-26 lite, P3-25 lite)

Goal: one command starts everything, one document says what to show, one script proves it works end to end.

- `pnpm demo` (`scripts/demo.mjs`): Docker (PostGIS + mail catcher) → build + migrate → API (with demo-only secrets and a CORS allow-list for the web app) → demo data → admin panel (Vite) → customer app (Flutter in Chrome). Ctrl-C stops what it started. `--no-app`, `--no-seed`.
- Demo data (`apps/api/scripts/seed-demo.mjs`, P3-26 lite): created through the real API (so every rule applies) plus ONE SQL statement for the first Super Admin (the API never creates one, by design). Idempotent (looks up by name/code). Seven drawers (two each in Bengaluru, Pune and Hyderabad, one in Delhi; 09:00–21:00 every day), categories, three item models with prices/deposits/slot rules, 12 units, a "Front desk" role + person, a customer, two sample bookings (one confirmed, one cancelled with refund). Local development databases ONLY.
- `docs/demo.md`: how to start, credentials, a 10-minute walkthrough, what is not in the demo.
- `pnpm demo:smoke` (P3-25 lite): headless browser drives the REAL admin panel and the REAL Flutter web app (sign in → find drawer → reserve → pay → view → cancel; every admin page) and saves screenshots. It needs the stack running, so it is a manual/pre-demo check, not a CI gate.
- Known automation quirk: Flutter web drops the first keystrokes after a focus change; the smoke script waits after each click and verifies the typed values (real users are unaffected).
