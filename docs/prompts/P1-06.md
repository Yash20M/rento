# P1-06 — Concurrency spike (SQL, HTTP-less)

## 1. Role
You are a senior backend/database engineer (PostgreSQL concurrency, Kysely, Vitest) on the Rento platform.

## 2. Context
- Product: time-based rental of individually-tracked assets. The product promise — "no double booking" — rests on the `no_overlapping_occupancy` exclusion constraint (README §9). This task is the **early proof** that the design holds under real parallel load, before any HTTP code exists.
- Architecture in play: real PostgreSQL+PostGIS (Testcontainers), `withTransaction` + error mapper from P1-05, the baseline schema from P1-04. No HTTP, no Nest.
- Relevant README sections: §9.3 (what the DB does under simultaneous requests), §9.4 (reference algorithm: `SKIP LOCKED` candidate, insert booking + occupancy, `23P01` → SAVEPOINT retry → `BOOKING_SLOT_TAKEN`), §16 (mandatory scenarios; concurrency suite is **required, never skipped**; flakiness is a bug signal).
- Existing code to read first: `src/db/{transaction.ts,errors.ts}`, `test/support/db/*`, `test/factories/index.ts`, `test/db/db-errors.db.spec.ts`, `db/migrations/0001_baseline.sql`.
- Decisions already made (do not revisit): READ COMMITTED (no SERIALIZABLE); `FOR UPDATE OF a SKIP LOCKED` fan-out; the DB constraint is the guarantee, the candidate query is an optimisation; app pool default 10 per instance.
- Out-of-scope neighbours: the production booking endpoint, validation, idempotency, hold expiry, payments → P2-22/P2-15/P2-23; HTTP-level concurrency suite and cancel/extend/block races → **P2-29**; k6 load tests → P4; `pgbench` variant → not needed (the Node suite already issues true parallel transactions).

## 3. Goal
`pnpm --filter api test:concurrency` proves, on a real PostGIS database and with truly parallel transactions, that: 50 simultaneous overlapping claims on one asset yield exactly 1 success and 49 `BOOKING_SLOT_TAKEN`; 50 claims on a pool of 3 assets yield exactly 3 successes on 3 distinct assets; non-overlapping claims never conflict; and a randomised mixed workload never violates the invariants — with no deadlocks, no lock timeouts and no unexpected errors. Each scenario repeats 5× on a fresh database.

## 4. Scope
**In scope**
- `test/support/booking-spike.ts`: `claimSlot()` — a *test-only prototype* of README §9.4 steps 5–7 (candidate selection with `FOR UPDATE OF a SKIP LOCKED`, insert `held` booking + `booking` occupancy `[start, end+buffer)`, SAVEPOINT retry on `23P01` up to 3 candidates, `SlotTakenError` otherwise) built on `withTransaction`.
- `test/support/concurrency.ts`: `warmPool`, `startTogether` (barrier so all tasks begin at once), outcome classifier, `findOverlaps` (README §16 query), `invariants()` helper.
- `test/concurrency/*.concurrency.spec.ts` and a vitest project `concurrency` + script `test:concurrency` (files run sequentially so CPU noise from other suites cannot hide or cause failures).
- Rounds: every scenario runs `CONCURRENCY_ROUNDS` (default **5**) times, each on a fresh clone of the migrated template.

**Out of scope**: see §2. `claimSlot` is not production code and is not exported from `src/`.

## 5. Detailed requirements
1. **Pool**: scenario pools are created with `max` = number of parallel tasks (50) so the database really sees 50 concurrent transactions; one scenario uses the app default (10) to prove queueing is also correct. Pools are warmed (all connections open) before the barrier is released.
2. **`claimSlot(db, input)`** where `input = { userId, drawerId, itemModelId, startsAt, endsAt, bufferMin }`: inside `withTransaction` (default 3 s `lock_timeout`):
   a. up to 3 attempts: select one available asset of `(drawerId, itemModelId)` with no live occupancy overlapping `[startsAt, endsAt + buffer)` and not already tried, `ORDER BY asset_code FOR UPDATE OF a SKIP LOCKED LIMIT 1`;
   b. `SAVEPOINT`; insert booking (`held`, `hold_expires_at = startsAt - 1 minute` placeholder, price 4900); insert occupancy (`kind='booking'`, `during = tstzrange(start, end + buffer, '[)')`); `RELEASE SAVEPOINT`;
   c. on raw SQLSTATE `23P01`: `ROLLBACK TO SAVEPOINT`, remember the asset, try again;
   d. no candidate / attempts exhausted → throw `SlotTakenError` (whole transaction rolls back).
   Returns `{ assetId, bookingId }`.
3. **Outcome classifier**: `ok` | `conflict` (`SlotTakenError`) | `retry_later` (`RetryLaterError`, i.e. lock timeout/statement timeout) | `other` (everything else, including deadlock `40P01`, pool timeouts, unmapped errors). Tests assert `other === 0` and `retry_later === 0` and print the raw error if not.
4. **Invariant helper** (run after every scenario, directly in SQL, independent of the code under test):
   - `findOverlaps` returns 0 rows (README §16 query);
   - number of live (`released_at IS NULL`) occupancies = number of `ok` outcomes;
   - number of bookings in the DB = number of `ok` outcomes (losers rolled back completely);
   - every live occupancy's `booking_id` exists and its booking's `asset_id` equals the occupancy's `asset_id`;
   - no two live occupancies share a `booking_id`.
5. **Scenarios** (each a round-parameterised test):
   - **C-01** 50 parallel claims, 1 asset, staggered overlapping starts (`i % 3 × 15 min`, 60-min duration, buffer 0) → 1 ok, 49 conflict.
   - **C-02** 50 parallel claims, 3 assets, identical window → exactly 3 ok on 3 distinct assets, 47 conflict.
   - **C-03** 20 parallel claims on 1 asset for back-to-back hourly windows `[10+i, 11+i)` → 20 ok, 0 conflicts (no false conflicts from GiST/locking).
   - **C-04** buffer semantics under parallelism (1 asset, buffer 15 min). Phase 1, in parallel: 10 claims for A=`[10:00,11:00)` and 10 for D=`[11:15,12:15)` → exactly 1 ok in A and 1 ok in D (A's occupancy ends 11:15, so D is adjacent, not overlapping). Phase 2, in parallel: 10 claims for E=`[11:00,12:00)` → 0 ok (overlaps A's buffer and D).
   - **C-05** randomised mixed workload (deterministic seeded PRNG for inputs): 50 claims, random starts on the quarter-hour within an 8-hour day, random 30–120 min durations, 3 assets → invariants hold; `ok + conflict = 50`; `ok ≥ 3`; no `other`/`retry_later`.
   - **C-06** 50 parallel claims, 1 asset, pool `max = 10` (app default) → 1 ok, 49 conflict, `pool.totalCount ≤ 10`.
   - **C-07** a rolled-back holder never leaves a ghost: tasks A (holds the slot, then throws) and 10 waiters → after A's rollback exactly 1 waiter wins, 9 conflict; invariants hold.
6. Each scenario asserts real parallelism: `pool.totalCount ≥ min(tasks, 40)` for 50-wide scenarios (pool was warmed to `tasks`).
7. Scripts: `test:concurrency` (`vitest run --project concurrency`). The project sets `fileParallelism: false`, `testTimeout` 120 s. Env `CONCURRENCY_ROUNDS` overrides the default 5.
8. The suite never uses `sleep`/timers to coordinate; ordering comes from the barrier and the database.

- [ ] AC-1 C-01: exactly 1 success / 49 conflicts, invariants hold, in all 5 rounds. → C-01
- [ ] AC-2 C-02: exactly 3 successes on 3 distinct assets / 47 conflicts. → C-02
- [ ] AC-3 No false conflicts for non-overlapping parallel claims. → C-03
- [ ] AC-4 Buffer semantics hold under parallelism. → C-04
- [ ] AC-5 Randomised mixed workload never violates any invariant. → C-05
- [ ] AC-6 Correct with the app-default pool (queueing). → C-06
- [ ] AC-7 A rolled-back holder frees the slot for exactly one waiter. → C-07
- [ ] AC-8 Zero deadlocks / lock timeouts / unexpected errors in every scenario. → all (`other === 0`, `retry_later === 0`)
- [ ] AC-9 The suite actually bites: removing the exclusion constraint makes it fail. → mutation check recorded in Evidence
- [ ] AC-10 Stable: the whole `test:concurrency` command run 5 consecutive times, all green. → recorded in Evidence
