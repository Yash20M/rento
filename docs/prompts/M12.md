# M12 — Browser session cookie (admin) and email verification in the app (fast track: P3-01 part, P3-12)

## Decisions (engineering defaults — flagged)

- **Admin session = ADR-012 target.** New routes `POST /v1/auth/session/login | refresh | logout`. The refresh token is an `HttpOnly; SameSite=Strict; Path=/v1/auth/session` cookie (`Secure` in production), never in a response body; the access token (memory only) is the only thing page scripts see. The demo shortcut (refresh token in `sessionStorage`) is gone. Reload → the SPA asks `session/refresh`, the browser attaches the cookie.
- **CSRF** on the cookie-authenticated calls: SameSite=Strict **plus** a required custom header (`X-Requested-With: rento-web`, which a foreign site cannot send without a CORS preflight the allow-list refuses) **plus** an Origin check (an `Origin` header, when present, must be an allowed origin or the API's own host). A dead cookie is cleared on refusal; reuse of a spent cookie revokes the whole session family (existing rotation logic).
- **CORS**: credentials are allowed **only** on `/v1/auth/session/*`; everywhere else sessions still travel in `Authorization`. The admin origin must be in `CORS_ALLOWED_ORIGINS` when it is served from another origin or behind a proxy (the demo script now does this).
- Accepting an invitation now starts a proper browser session by signing in with the password just chosen (the invitation's own response is ignored).
- **App email verification**: account-tab tile (unverified → "Verify your email", verified → "Email verified"), a screen to paste the code from the emailed link or ask for a new link (rate limit explained); the tile updates without a restart. Real-restart journey tested at the widget level (register → restart → still signed in → sign out → next restart signed out).
- Still open on P3-01: Google sign-in on the admin login (needs a Google client id), Playwright e2e against the real stack, dedicated 401/403 pages.
